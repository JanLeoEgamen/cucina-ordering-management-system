# Database

SQLite by default (`DB_CONNECTION=sqlite`); the schema is portable to MySQL (the code avoids SQLite-only SQL).
Source of truth: `database/migrations/`. `scripts/harness.php` fails if a created table is missing here (write each as `` `table` ``).

## Conventions

- Custom primary key names: `dish_id`, `dish_type_id`, `method_id`, `session_id`, `session_dish_id`, `order_id`, `order_item_id`.
  (`payments` uses `order_id` as its primary key: one payment per order.)
- Almost every domain table has `is_active` (bool) + `deleted_at` (soft delete) + timestamps. Always filter `whereNull('deleted_at')`.
- Models are thin: reads/writes are **static query-builder methods** (`Dish::getAll()`, `Order::createOrder()`), returning `stdClass`/arrays, not Eloquent chains.
- Migration filenames use a `2026_11_*` prefix; keep new ones later than the latest existing file.

### Pre-orders
A parallel set of tables, **not** a type flag on `order_sessions` / `orders` (those assume one menu, stock and a separate `payments` table). Migrations `2026_11_13_2001..2004` created them as `bulk_sessions` / `bulk_session_dishes` / `bulk_orders` / `bulk_order_items` (the feature used to be called "bulk orders"); `2026_11_19_210000_rename_bulk_orders_to_pre_orders` renamed the tables, their `bulk_*_id` columns, the permissions, the `bulk_orders.*` settings keys and the `BLK-` order numbers, keeping the data. Run `php artisan migrate`. All four are soft-deleted like the rest.

| Table | Columns / notes |
|---|---|
| `pre_order_sessions` | `pre_order_session_id`, `created_by` → users, `title?`, `order_date`, `start_time`, `end_time`, `min_quantity` (fewest plates, all dishes together, one order must hold; default 10), `ended_at?`, `is_active`. **Status is computed** like an order session (`PreOrderSession::statusOf`). Like order sessions, two open windows may not overlap (`PreOrderSession::overlaps`, enforced by the controller). |
| `pre_order_session_dishes` | Dishes offered in a pre-order session: `pre_order_session_id`, `dish_id` (unique pair), `is_available`, `is_active`. **No stock columns**: a pre-order session has no limit. A dish removed from the session is soft-deleted, not dropped (order lines point at it). |
| `pre_orders` | `pre_order_id`, `pre_order_session_id`, `user_id`, `order_number` unique (`PRE-YYYYMMDD-NNNN`, own counter), `order_date`, `total_amount`, `order_status` (`pending`/`completed`/`cancelled`), and the **payment inline** (a pre-order has exactly one): `payment_method_id` → payment_methods, `payment_status` (`pending`/`verified`/`rejected`), `reference_number?`, `proof_of_payment?`, `rejection_reason?` (500), `verified_by?` → users, `verified_at?`. |

## Relationships (summary)

```
users 1─* order_sessions 1─* session_dishes *─1 dishes *─* dish_types
                  │                  │
                  └─* orders 1─* order_items ──┘ (via session_dish_id)
                        │
                        ├─1 payments *─1 payment_methods
                        └─* discounts (optional: a copy of its name / percent is kept on the order)

users 1─* pre_order_sessions 1─* pre_order_session_dishes *─1 dishes
                  │                  │
                  └─* pre_orders 1─* pre_order_items ──┘ (via pre_order_session_dish_id)
                        ├─* payment_methods (payment is inline)
                        └─* discounts (optional, same copy)
```

## Seeding

`php artisan migrate:fresh --seed` (or `db:seed`) runs `DatabaseSeeder`: test user + admin account → `UserSeeder` (Jan Leo Egamen, `jleoegamen6@gmail.com`; password `Password123!` unless `SEED_USER_PASSWORD` is set in `.env`) → `PermissionSeeder` (permissions, the Super Admin and Customer roles, and Super Admin attached to every account in `PermissionSeeder::SUPER_ADMIN_EMAILS`, so a new owner account is added there **and** created before this step)
→ payment methods (Cash on Pick up, GCash, Bank Transfer) → `CompanySeeder` (*Bounty Fresh Inc.*, *Bounty Plus Inc.* and *Guest*, which is protected: `Company::PROTECTED`, edit and delete answer 422; without a company the required register dropdown is empty; an existing name is left as it is, so a renamed or switched-off company is not put back; run it alone with `php artisan db:seed --class=CompanySeeder`) → `MenuSeeder`.

`MenuSeeder` loads the real menu from two files in `database/seeders/data/`: `dish_types.csv` (every dish type + its description, 17 of them, all seeded even if no dish uses one yet) and `menu.csv` (one row per dish: **Dish Type Names**, name, description, price, calories, ingredients). A dish can be in many types, so "Dish Type Names" lists all of them separated by `;` (e.g. `Breakfast; Silog`); never write two types as `A / B`. A type named in `menu.csv` but missing from `dish_types.csv` is still created (without a description). A database seeded earlier with a combined type such as `Breakfast / Silog` is converted on the next run: its dishes move to `Breakfast` and `Silog` and the combined type is soft deleted (only when every part is a known type, so an admin-made `Kids / Party` stays). Types and dishes are matched by name and only created when missing, so re-running keeps prices and edits made in the app; the CSV carries a real price on every dish (a starting point, edited in the app; a price of 0 or less makes the seeder throw), and a dish already stored at 0.00 gets the CSV price on the next run. A picture named after the dish slug in `database/seeders/data/images/` (e.g. `chicken-adobo.jpg`; jpg, jpeg, png, webp) is copied to the `public` disk (`dishes/`) and attached to a dish that has no image. `DishTypeSeeder` / `DishSeeder` are the older demo menu, now only run with `--class`. Load the real menu into an existing database with `php artisan db:seed --class=MenuSeeder`.
Seeders use `firstOrCreate` / `insertOrIgnore`, so they can be re-run.
