# Architecture

**Cucina Ordering Management System** — a kitchen/canteen ordering app. Staff publish an *order session* (a time window
with a limited stock of dishes); customers order from the live menu and pay by cash on pickup or bank/e-wallet (with
proof upload). Admins manage dishes and their types (one **Dish Masterlist** page), payment methods, sessions, roles and users.

## Stack

| Layer | Choice |
|---|---|
| Backend | PHP ^8.2, Laravel 12 (monolith, server-rendered) |
| Auth | Laravel Breeze (session) |
| Permissions | spatie/laravel-permission ^8 |
| Google sign-in | laravel/socialite ^5 (optional, needs `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`) |
| Tables | yajra/laravel-datatables-oracle (server feed) + datatables.net (browser) |
| Frontend | Blade, Alpine.js 3, Tailwind 3, Vite 6, axios |
| DB / cache / queue / session | SQLite locally, MySQL when the app is deployed; `file` driver for cache and sessions (no network trip), `database` for the queue |
| Tests | PHPUnit 11 (`php artisan test`), SQLite in-memory |

## Request flow

```
Route (routes/web.php, group: auth)
  → Controller::middleware()  permission:<name>          (authorisation)
  → Controller action         $request->validate()       (validation)
  → Model static method       DB query builder           (data access)
  → View (Blade) | JSON {status,message} | DataTables JSON
```

## Key conventions (follow them — the codebase is consistent)

1. **Query-builder models.** `app/Models/*` expose `public static` methods (`getAll`, `findById`, `existsById`,
   `create…`, `update…`, `delete…`) over `DB::table()`. Eloquent is only kept where a package needs it (`User`, `Role`).
   Define table/column constants at the top of the model.
2. **IDs in routes are raw ints** (`{id}` + `whereNumber`); controllers cast with `(int) $id`.
3. **Responses** use `Controller::successResponse()` / `errorResponse()`; never invent another JSON shape.
4. **Authorisation lives in the controller's `middleware()`**, one `permission:` entry per action.
5. **Soft deletes + `is_active`** everywhere; reads filter `deleted_at IS NULL`.
6. **Business rules in the controller + model, not the view.** Examples: protected roles/payment methods, "creator ends the session", "no delete while it has orders".
7. **Money is `decimal(10,2)`**, line prices are copied into `order_items` at order time.
8. **Stock** is changed only through `SessionDish::reserve()` / `release()` (conditional UPDATE) inside a transaction.
9. **Soft navigation.** Sidebar (and dashboard tile) links do not reload the browser: `resources/js/ui/soft-nav.js` swaps `#page-root` and starts / stops the page's script module (`pages/*.js`, `export default start`, named by `<x-page-module>`). Keep a signed-in view's page area free of `<script>` tags and keep page state inside `start()`; see [frontend.md](frontend.md).
10. **Comments explain *why*, in plain sentences**; the codebase uses `' . '` string concatenation with spaces
   (Pint's default would rewrite it — do **not** run `pint` over existing files).

## Domain model

- `Dish` ↔ `DishType` many-to-many.
- `User` belongs to one `Company` (`users.company_id`, **required** by every form, picked from a dropdown). Companies are their own CRUD (Companies page, `view|create|edit|delete companies`, soft delete + `is_active`): an inactive company is no longer offered but keeps its people, and a company with live users cannot be deleted. Shared validation is `Company::rules($currentId)`; `CompanySeeder` seeds *Bounty Fresh Inc.*, *Bounty Plus Inc.* and the protected *Guest* (`Company::PROTECTED`, locked by name like `PaymentMethod::PROTECTED`: it cannot be edited or deleted, only chosen).
- `OrderSession` has many `SessionDish` (a dish + its stock for that window). Only **one session may be `live`** at a time (`OrderSession::live()` returns the first).
- `Order` belongs to a session and a user; has many `OrderItem` (→ `SessionDish`); has one `Payment` (→ `PaymentMethod`).
- **Discounts** (`Discount`, its own CRUD page, `view|create|edit|delete discounts`; soft delete + `is_active`; a name, a **percent of the whole order subtotal**, a *requires proof* switch and optional valid-from / valid-until dates). A customer **picks one at checkout** (one per order, no stacking). The switch **System Configuration → Discounts** (`Setting::discountMode()`: `off` default / `orders` / `pre_orders` / `both`) decides where any is offered; it is read fresh on every checkout. The shared rules live in `App\Support\OrderDiscount` (used by `OrderController` and `PreOrderController`), and **the server does all the math** from the percent it finds at that moment (`Discount::usable()`, `Discount::amounts()`; a percent that moved since the cart was drawn is refused like a price change). The order stores a **copy** (`discount_name`, `discount_percent`, `subtotal_amount`, `discount_amount`; `total_amount` = what is paid, and the payment's `amount` follows it), so editing or deleting a discount never rewrites an order. **Review state machine** (`orders.discount_status`): `none` → (a discount that needs no ID) `approved` at once, or (one that needs an ID, uploaded to the **private** disk) `pending` → `approved` | `rejected`, decided by staff with `review discounts` (`OrderDiscountController`, under the order's row lock). **A rejected discount can go back to `pending`** when its customer sends a new ID (`OrderController::resubmitDiscountProof`, same pattern as fixing a rejected payment): the discount is applied again from the copy on the order, the payment's amount follows, a bank / e-wallet payment still waiting at the full price is sent back, and it is refused once that payment was verified, when the order is no longer `pending`, or while the switch is off. While `pending`, the order's payment cannot be verified and the order cannot be completed or announced as ready (the price is not final). **Rejecting** takes the discount off: the total goes back to the subtotal, the payment's amount follows, and a bank / e-wallet payment that was paid for the smaller amount is sent back (rejected with a reason naming the new total; the plates stay held; the customer sends a new proof or switches to cash, the existing way out). Cash on Pick up just owes the new total at the counter. Notified through `OrderNotifier` (`discountApproved` / `discountRejected`, customer + watchers). **Pre-orders:** the customer side is done (menu picker, stored copy, ID, My Pre-Orders), but staff cannot decide a pre-order's discount yet because the pre-order lifecycle itself (verify / complete / cancel and a staff page of pre-orders) is not built: see known-issues D2.
- **Ala carte (a plate without rice).** Staff tick **Comes with rice** on a dish (`dishes.includes_rice`, default off: nothing changes until they do) and set, in **System Configuration → Ala carte (no rice)**, where it is offered (`ala_carte.mode`: `off` default / `orders` / `pre_orders` / `both`, like the discounts switch) and the **rice price** (`ala_carte.rice_price`, pesos taken off **each plate** ordered without rice). `Setting::alaCarteFor($kind)` is on only with a covering mode **and** a price above 0. A customer picks, per dish in the cart, **how many of its plates go without rice** (a stepper in the menu's cart line, a "Without rice" row on a pre-order dish card; the JS only previews). The shared server rules are `App\Support\AlaCarte` (used by `OrderController` and `PreOrderController`): `judge()` checks the switch, the dish flag (a dish is offered only while it comes with rice **and** costs more than the rice), the count against the quantity and the rice price the cart showed; `lines()` splits a dish into a **with rice** line at the dish price and a **without rice** line (`order_items.no_rice` / `pre_order_items.no_rice`) at `price − rice`, never below 0. So **one dish can have two lines in one order**: stock is still taken for the whole quantity (a plate is a plate), the line's `unit_price` is a copy (a later rice price never rewrites an order), the discount applies to the subtotal that already has the deduction, and the item readers (`OrderItem` / `PreOrderItem::itemsByOrder`, `ofOrder`) print the line as **"Dish (no rice)"** in `dish_name`, so every popup, export, notification and Google Chat message shows it with no change. Never key order lines by `session_dish_id` (`takenByOrder` sums them). A refused order carries `ala_carte` (switch, price, the dishes that can go without rice) so the menu corrects itself; the live stock poll carries only the switch and the price.
- State machines:
  - session: `scheduled → live → ended` (computed from time + `ended_at` + `is_active`)
  - order: `pending → completed | cancelled` (staff can also **announce it ready for pick up**: `orders.ready_at` is set and the customer is notified, but the order stays `pending`; same payment rule as completing, announced once) — both are built (`POST /orders/{id}/complete`, `POST /orders/{id}/cancel`); only a pending order moves; staff cancel with `cancel orders`, and a customer can cancel their **own** pending order (`POST /my-orders/{id}/cancel`) only while System Configuration → *Customers can cancel their own order* is on (off by default); both run the same `OrderController::cancelOrder`
  - payment: `pending → verified | rejected` (mirrored on `orders.payment_status`); a **rejected** payment on a still-pending order goes back to `pending` when its customer sends a new proof or switches to Cash on Pick up (`POST /my-orders/{id}/payment/proof|cash`) — the order and its reserved plates stay as they are meanwhile
  - **Payment rules by method:** *Cash on Pick up* is paid at the counter, so its payment is **verified when the order is completed** (no separate verify / reject). Any other method is paid first: its payment can be **verified or rejected as soon as the order exists**, and the order can only be **completed once that payment is verified**. A completed or cancelled order's payment decision cannot be undone.
  - **Cancelling** a pending order gives its reserved stock back (`SessionDish::release`) and rejects a payment that was still pending (reason "The order was cancelled."). A **verified** payment blocks it: undo the verification first. A cancelled order's payment can no longer be verified, rejected or undone.

## Pre-orders (separate from the menu)

A second, parallel ordering feature: staff open a **pre-order session** (a window like an order session, plus `min_quantity` plates per order; System Configuration sets the minimum and maximum plates of any pre-order, and a session may ask for more than the minimum, never less) and customers order big quantities from a **separate pre-order menu**. Decided with the owner: customers order themselves; the dishes come from the same Dish Masterlist; **no stock** (the kitchen decides its capacity); the same payment methods, but its own pages, not the Orders / Payments pages.

It is its own tables and models (`PreOrderSession`, `PreOrderSessionDish`, `PreOrder`, `PreOrderItem`), **not** a `session_type` column: `orders.session_id` / `order_items.session_dish_id` are NOT NULL stock links, and the menu, dashboard, welcome page, `Order::list`, `Payment::listQuery`, `orderRow()`, `OrderNotifier` and the order popup all assume one kind of session. The payment is stored on `pre_orders` itself (one per order), so an order and its payment change state under the same row lock (`PreOrder::lockedState`). Same payment rules as orders (cash is verified by completing, others verified first; a verified payment blocks cancel) apply. At most **one open pre-order session at a time** (overlap check, unlike order sessions). Status of this work: **data layer, permissions, factories, the staff Pre-Order Sessions page (`PreOrderSessionController`) and customer ordering (`PreOrderController`: pre-order menu, place order, My Pre-Orders) done; the order lifecycle (complete / cancel / verify / reject / undo, fixing a rejected payment), notifications and the session page's orders table follow** (see changelog). A placed pre-order is `pending` with a `pending` payment and nothing can move it yet.

## Notifications

In-app notifications (a bell with an unread badge and a **Notifications** page), written by `App\Support\OrderNotifier` into `user_notifications` (`UserNotification` model, query builder). Call **one** method **after** the event has been saved and its transaction has committed — never inside the transaction:

| Event | Called from | Customer of the order | Watchers |
|---|---|---|---|
| `placed` | `OrderController::placeOrder` | "Order X placed" (+ how to pay) | "Jane placed order X" |
| `paymentVerified` / `paymentRejected` (+ reason) | `PaymentController::decide` | "Payment verified" / "Payment rejected" (reason + the way out) | copy, in staff words |
| `completed` | `OrderController::complete` | "Order X completed" | copy |
| `cancelled` | `OrderController::cancel` | "Order X cancelled" | copy |
| `paymentResent` (new proof / switched to cash) | `OrderController::resubmitProof` / `switchToCash` | — | "Jane sent a new proof" / "Jane will pay X in cash" |
| `ready` (orders announced ready for pick up; one order or a whole session) | `OrderController::ready` / `OrderSessionController::announceReady` | "Order X is ready for pick up" (+ pay cash / show the number) | one line for the announcement ("Jane's order was announced as ready", or "N orders are ready") |
| `soldOut` | `OrderController::placeOrder` | — | "Adobo is sold out" (once per dish per 2 minutes) |
| `sessionOpened` | `OrderSessionController::store` | everyone with `view menu` except the publisher: "A new order session is open" + date and hours + the available dishes with prices (first 6), linking the menu (job kind `session-opened`, one bulk insert) | — |

**Watchers** are the users picked in System Configuration → Notifications (`Setting::notificationWatchers()`, JSON in the `settings` table): they get a copy of every event of every customer, except the one they caused themselves, and the staff-only events above. A customer who is also a watcher gets one notification, in their own words.

**Queued, so a rush cannot hurt:** the request only pushes a small job (`App\Jobs\DeliverNotification`, one row in `jobs`) on the `notifications` queue (`config/notifications.php`, env `NOTIFICATIONS_QUEUE`) inside `rescue()`, so a customer never waits and a notification that cannot even be queued never fails an order. A **queue worker does the rest** at its own pace: 3 tries with 5 s / 30 s backoff, a `failed()` log line when it gives up, failed jobs pruned after a week (`queue:prune-failed`). The sold-out check is done in the request with one indexed read, and its job is pushed only when a dish really hit zero. **Retry-safe:** the ONE bulk insert is a single statement and comes after everything that can fail, so a retry can neither lose nor duplicate rows.

**Plain AJAX, no websocket:** the bell polls `GET /notifications/feed?after=N` about every second (a count + an indexed range read, almost always empty; paused while the tab is hidden), so a notification appears within seconds without a refresh. The bell sits in the **top right corner** of every page (a sticky bar from `lg`, the phone top bar below it) with the dark / light switch and the account menu; opening it lists the latest 6 (`?recent=1`, read only then), and a new arrival swings it and toasts. Reverb / websockets were tried and removed on purpose: one less long-running process to run and watch. One event = the order (one join query), the people (one query), **one bulk INSERT**; the text is stored ready to print; read rows are pruned daily by `notifications:prune` (`Schedule`, needs `schedule:work` / the server cron).

**Google Chat copy (optional, System Configuration → Notifications → *Send notifications to Google Chat*, default off):** `OrderNotifier::copies()` (after `insertMany()`, inside `rescue()`) pushes, besides the email job, ONE `App\Jobs\SendGoogleChatMessages` (same queue, `tries = 1`) carrying the same title / text / link per person. The worker reads the people's Google ids in one query and `App\Support\GoogleChat` sends each a **direct message from the Chat app** (service account key at `GOOGLE_CHAT_CREDENTIALS`, scope `chat.bot`, token signed in-house and cached). A person is found by `users.google_id` (`spaces.findDirectMessage`, the space cached 30 days, a miss 10 minutes); someone who never signed in with Google, or never added the app in Google Chat, is skipped silently (they still have the bell and email). Each message is **plain text, not a card** (`GoogleChat::format`; a card showed as "sent an attachment" in Chat's notification preview, text shows its first line): an icon + the bell's title in bold, the words, for an order its **dishes with quantity and price, the total and the payment method** (the job reads them for the whole event in two queries, from the `order_id` / `type` that `mailRow()` carries) and a `👉` link on its own line ("Open order"). An entry may also carry `chat_body` (replaces the body here), `points` (lines printed as they are, under an optional bold `points_title`) and `button` (the link's label): the session-opened message uses them for its "Available now" dish list and "Open menu". The syntax follows the app's *Markup syntax* (`GOOGLE_CHAT_MARKUP`: `markdown` default, or `legacy`). **After a Google sign-in** the layout draws a one-time prompt (`<x-google-chat-prompt>`, `GoogleChat::shouldPrompt`) that checks the sync, sends the Welcome if they are synced, or offers the install guide (once per login, **at every login until they are synced**: *Maybe later* only closes it for the visit and stores nothing). **The first message anyone gets is a Welcome** (`GoogleChat::welcome`): sent the first time the Profile page finds them synced, or just before their first notification if that comes first, once per person (`users.google_chat_welcomed_at`, claimed with one conditional UPDATE so two requests cannot both send it, given back if Google refuses). Every failure is logged (with Google's reason) and swallowed; `php artisan google-chat:test {email}` checks the whole path for one person. Setup: `.env.example`.

**Email copy (optional, System Configuration → Notifications → *Send notifications by email*, default off):** when on, `OrderNotifier` pushes ONE more job after the in-app rows are saved — `App\Jobs\SendNotificationEmails` on the same queue, carrying one entry per person told (same title, text and link as the bell) — and the worker sends a `App\Mail\NotificationMail` (markdown view `emails/notification`) to each person's account address. One job per event, not per person. It is **not retried** (`tries = 1`, a retry would email everyone twice); each address is tried on its own and a failure is logged and skipped, and the push is inside `rescue()` so a mail problem can never fail the delivery job (whose retry would write the bell rows twice). The mail server comes from `.env` (`MAIL_*`; the default `log` mailer only writes to the log).

**Running it (one long-lived process besides the web server):** `php artisan queue:work --queue=notifications,default --tries=3 --max-time=3600` under Supervisor / systemd, restarted on every deploy (`php artisan queue:restart`), plus the scheduler cron. `composer dev` starts the worker locally. Without the worker nobody is notified (orders still work; the jobs wait in `jobs`). **Never run production with `QUEUE_CONNECTION=sync`**: the request then delivers everything itself (measured with 40 customers and email on: ONE "Add Session" click sent 42 emails inside the request, 2.7 s with the fast `log` mailer, far more with real SMTP, and the same for every order placed). On cPanel / shared hosting, where nothing can stay running, keep `QUEUE_CONNECTION=database` and run the worker from cron every minute: `* * * * * cd /home/USER/app && php artisan queue:work --queue=notifications,default --tries=3 --stop-when-empty --max-time=55` (it keeps polling for 55 s, so a notification still lands within a few seconds).

## Audit trail

Every person's activity is written to `audit_logs` (`AuditLog` model, query builder, append only) by **one middleware, not by calls in controllers**: `App\Http\Middleware\AuditTrail` is in the `web` group, so a new route is covered the moment it exists. `handle()` notes who is acting and, for a route whose prefix is in `config/audit.php` `subjects`, the record as it was (label + values); `terminate()` runs after the response and writes the entry with the final status and the record's after-state diff. Sign in / out / failed sign in / lockout / registration / password reset come from Laravel's auth events (`App\Listeners\AuditAuthEvents`, subscribed in `AppServiceProvider`). The logic is in `App\Support\Audit`. Both entry points are inside `rescue()`: **an audit failure is logged and never reaches the request**. Viewing is `AuditLogController` (list, one entry, CSV; `view audit-logs`), retention is `audit:prune` (daily, `AUDIT_RETENTION_DAYS`). Rules, privacy and what is never stored: [security.md](security.md#audit-trail). A new action needs no audit code; a new state change that should read well adds a line to `config/audit.php` `actions`, and a new `{id}` resource adds its prefix to `subjects`.

## Help and Support page

A public page, `GET /support` (`SupportController`, no login, no form: visitors who cannot sign in need it most), configured in **System Configuration → Support** (`edit settings`, no new permission): `support.email`, `support.phone`, `support.hours` (each shown only when set) and `support.content`, a Markdown FAQ that defaults to the built-in `resources/support/default.md`, read together by `Setting::support()`. The Markdown goes through `App\Support\SafeMarkdown` (shared with the legal pages); the page shell is the `<x-public-page>` component (shared with them too). Support is deliberately **not** a ticket system: nobody writes to the app, people are sent to the shop's own email / phone. If tickets are wanted later they are a separate feature (own tables, a `view support-tickets` permission, notifications through `OrderNotifier`).

## Legal pages (privacy policy, terms of service)

Two public pages, `GET /privacy-policy` and `GET /terms-of-service` (one `LegalPageController::show()`, route default `page`; no login: the sign in and sign up pages link to them), each with its own text in **System Configuration** (cards *Privacy policy* and *Terms of service*, `edit settings`, no new permission). Per page two settings, `privacy_policy.content` / `terms_of_service.content` (Markdown) and the matching `.contact_email`, read together by `Setting::legalPage($page)` (pages are listed in `Setting::LEGAL_PAGES`). Until an admin saves their own text a page shows its built-in text, `resources/legal/<page>.md` (the privacy text names what the app collects, the policy text the rules of ordering; `{app_name}` becomes the app's name). A third page = a `LEGAL_PAGES` entry + defaults + a title in `LegalPageController::TITLES` + a route + a card include. The form's text box is prefilled with whatever the page shows, and saving the built-in text unchanged, or an empty box, stores nothing, so the page keeps following the built-in text. "Last updated" is the `updated_at` of the page's two rows, so `Setting::setLegalPage()` writes only a value that changed. The Markdown is rendered with raw HTML escaped and unsafe links dropped (see [security.md](security.md)). Links to them: welcome footer, sign in / sign up pages, the register form and the account menu.

## Performance: queries are the cost

When the database is on another machine, **each query is a network round trip** (measured: ~350 ms to a remote MySQL, a new connection ~1.2 s; PHP itself is under 5 ms), so an endpoint's time is its number of queries. `php scripts/profile-endpoints.php` times every GET endpoint in-process and prints ms, query count and ms in queries (`--only=orders --sql` lists the SQL). What keeps requests cheap:

- **Sessions and cache are files** (`SESSION_DRIVER=file`, `CACHE_STORE=file`), not tables: no session read / write, no permission-cache read per request.
- **`Setting` reads one cached array** (`Setting::all()`, key `settings.all`, forever) instead of a query per key; `Setting::set()` forgets it after commit. Never `DB::table('settings')` for a read.
- **The bell poll (`UserNotification::state()`) is cached per person** (60 s at most) and forgotten by `insertMany` / `markRead` / `markAllRead`; a poll with nothing new runs no notification query and skips the list read. A new write path to `user_notifications` must forget `notifications.state.{id}` too.
- **`PaymentMethod::activeOptions()` is remembered for the request** (cash + bank options were two identical queries); the writes forget it.
- **`DB_PERSISTENT=true`** keeps the MySQL connection between web requests of a PHP worker; `AppServiceProvider::sendConnectionSetupOnce()` then sends `SET NAMES` + strict `sql_mode` once as the connection's init command instead of on every request, and skips Laravel's redundant `use db` (`use_db_after_connecting=false`) (web only; the console keeps Laravel's normal setup). Leave it off when a proxy such as ProxySQL / PgBouncer-style pooling sits in front, or if a PHP fatal error leaving a transaction open on a reused connection worries you.
- **The signed-in user is cached** (`App\Auth\CachedUserProvider` + `App\Support\AuthCache`, config `auth.cache_ttl` / env `AUTH_CACHE_TTL`, 300 s, 0 = off): the session's user comes from the cache with their roles and direct permissions preloaded, so identifying the person and the `permission:` middleware cost **no query** (they were 3 round trips on every request, and every bell / stock poll). It is never served stale: see **One listener drops every cached read** below.
- **Master data and the staff feeds are cached with their tables** (`App\Support\TableCache::remember($tables, $key, $closure)`): dishes, dish types, companies, roles, users, payment methods, the orders / payments feeds, the order and pre-order session rows, the pending-payments count and a customer's plain My Orders pages. A cached read carries the version of each table it names; a write to any of them gives that table a new version, so the old entry is never asked for again.
- **One listener drops every cached read** (`TableCache::watch()`, booted in `AppServiceProvider`): it looks at every non-SELECT statement the app runs, from any process (web, console, queue worker, seeder), and only **notes** the table it writes (`TableCache` ignores `cache`, `sessions`, `jobs`, `migrations`, `audit_logs`, `user_notifications`). It does **no cache work inside that event**: the tables are given a new version right before the next cached read, and once more when the transaction commits, the request ends or a queue job ends (so a reader that looked between the write and its commit cannot keep the old rows). A finished migration (`MigrationsEnded`) flushes the whole cache, because `migrate:fresh` changes every row without a statement the listener understands and a file cache survives it. Writes to `users`, `roles`, `permissions` and the three spatie pivots also bump the auth epoch. No controller or model has to clear anything. **Rules for a new cached read:** (1) it must depend ONLY on the rows of the tables you name: no `now()`, no auth user, no request value (a status computed from the clock is worked out AFTER the cached rows, see `OrderSession::getAll`); (2) name EVERY table it reads, including joined ones and the ones a foreign-key cascade writes to (a cascade is not a statement the listener sees); (3) never put free text a customer types into the key (`Order::pageOfUser` caches only plain views, otherwise a search would create a cache file per keystroke). The TTL (10 min, `TableCache::TTL`) only covers rows edited by hand in the database and another server's cache.
- Left per request on a warm cache: the page's own uncached reads (the live session, a customer's search, the dashboard's live session). A **cold** request after a write pays the real queries once. With several app servers the file cache is per server: set `AUTH_CACHE_TTL=0` and move the cache to Redis (a shared cache makes the listener's bumps visible to all).

- **The web server compresses and caches** (`public/.htaccess`, Apache; each rule is inside an `<IfModule>`, so a server without the module just ignores it): text responses (HTML, JSON feeds, CSS, JS, SVG) go through `mod_deflate` (the pages are 80-350 KB of HTML and shrink to ~10-15 %), and `/build/*` (hashed Vite files) is sent with `Cache-Control: public, max-age=31536000, immutable`. **On nginx** put the same in the server block: `gzip on; gzip_types text/css application/javascript application/json image/svg+xml;` and `location /build/ { expires 1y; add_header Cache-Control "public, immutable"; }`. Check on a deployed site with `curl -sI -H 'Accept-Encoding: gzip' https://site/build/assets/<file>.js` (look for `Content-Encoding: gzip` and the `Cache-Control` line; send a browser User-Agent, a plain curl one may be answered 406 by a firewall rule).

- **Finding out why a request is slow on a server** (`SERVER_TIMING=true` in `.env`, `App\Http\Middleware\ServerTiming`, off by default): people who can `view audit-logs` get a `Server-Timing: boot;dur=…, total;dur=…, db;dur=…;desc="N queries", php;desc="<sapi>, opcache on|OFF"` header (`boot` = framework start-up, `php` = how the web server runs PHP: `fpm-fcgi` is PHP-FPM, `cgi-fcgi` / `apache2handler` are not, and whether OPcache is on for the WEBSITE, which the command line cannot tell), shown by Chrome / Edge DevTools in Network → the request → Timing → *Server Timing*. **"Waiting for server response" minus `total` is time spent before PHP started** (web server queue, a busy PHP pool, TLS): that gap is the host, not the code; `db` and the query count are the code. Work done AFTER the response (the audit trail row, cache versions) cannot be in a header: when it takes over 200 ms it is logged (`Slow after-response work: … ms`). **Under PHP-FPM** the browser is released before that work (`fastcgi_finish_request`); under mod_php / suPHP / CGI it keeps waiting, which looks like a long *Content download* for a tiny JSON reply: on cPanel switch the domain to **PHP-FPM** in MultiPHP Manager.

- **`php artisan perf:check`** (run it on the server) times, one by one, what a write request needs: a database SELECT, an INSERT with its own commit, the same inserts in one transaction, a cache write / read and a locked file write, and prints the PHP / cache / session / queue settings, whether config + routes are cached and whether OPcache is loaded. It uses a scratch table of its own (`zz_perf_check_xxxx`, dropped in a `finally`) and touches no app table. A commit over ~15 ms means the database disk is slow, and every write request pays it once per statement that is not inside a transaction.

- **Big staff tables are paged by the server (F22).** The Orders and Payments tables grow with every order, and they used to receive EVERY row (measured at 5,000 orders: 8 MB of JSON, 2.2-2.8 s and 150-226 MB of PHP memory, i.e. out of memory on a 128 MB host around 3,000 orders). They are DataTables in `serverSide: true` mode: a request that carries `draw` gets ONE page from `Order::staffPage()` / `Payment::staffPage()` (filters, `ServerTable::search()` word search, a whitelisted sort, `COUNT`, `LIMIT`; `OrderItem::itemsByOrder` for that page's lines), decorated and sent through yajra with its own search / order switched off (`->filter(fn () => null)->order(fn () => null)`, `setTotalRecords` / `setFilteredRecords`), plus `filters` (the method and session dropdown options, `Order::staffFilterOptions()`, cached with its tables). Measured at 5,000 orders: **a page is ~20 ms, 18 KB, ~44 MB** (the same for 50 orders or 50,000). A request WITHOUT `draw` still returns everything (scripts, tests, `scripts/profile-endpoints.php`). `App\Support\ServerTable` reads the request (`length` capped at 500, -1 not honoured, at most 6 search words, an unknown filter value filters nothing, `LIKE` wildcards escaped with `!`). The browser side: the filters are sent from `ajax.data`, the running number is `page.info().start + row`, the dropdowns are filled from `ajax.json().filters`, and **Export** (`table-export.js`) fetches the matching rows from the server 500 at a time (up to 5,000, with a toast when there are more) and renders them through a hidden throw-away DataTable built from the page's own column definitions, so the file reads like the table. New indexes for the filters and sorts: migration `2026_11_24_100000` (see database.md). **To page another table:** copy the pattern (a `staffPage` in its model, the `draw` branch in its controller, `serverSide: true` + `ajax.data` in its page module, filter options from the server); the other staff tables (sessions, dishes, users, roles, companies, discounts, payment methods) stay client-side on purpose, since none grows per order.
