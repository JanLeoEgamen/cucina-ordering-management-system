# Frontend

Blade + Alpine.js + Tailwind CSS 3 + Vite. DataTables for tables. No Flowbite, no SPA framework.

| `resources/js/ui/soft-nav.js` | Loaded on every page via `app.js`. **Soft navigation**: a click on a link inside a `[data-soft-nav]` region (the sidebar `<nav>`, its brand link, the phone top bar's logo, the dashboard's *Jump to* grid) is fetched as HTML and only `#page-root` (the heading + `<main>`, drawn by `layouts/app`) is swapped; sidebar, bell, theme, toasts and the Alpine root stay. It also updates the title, the sidebar's active link and the folded-group state, pushes history (back / forward re-visit without a push, scroll is saved in `history.state` and `scrollRestoration` is manual), moves focus to `<main>`, and shows a thin progress bar only when a visit takes more than 150 ms. **It is also what starts the page's script**: it reads `[data-page-module]` markers (`<x-page-module name="companies" />` in the view's `@push('scripts')`), imports `pages/<name>.js` (`import.meta.glob`, lazy chunk) and calls its default export `start()` on every visit; while `start()` runs, `document.addEventListener` / `window.addEventListener` are wrapped to carry an `AbortSignal` that aborts when the page is left, so **a page module may register document / window listeners freely and they never outlive it**. Anything else that outlives a visit (a timer, an observer, a `body` child) must stop by itself (menu.js polls only while `#menu-root.isConnected`; `row-menu.js` marks `<main>`, not a module variable, as wired; a page module must never keep state in a module level variable). **Falls back to a normal page load** (so the worst case is the old behaviour) for: a non-HTML or non-OK answer, a page without `#page-root` (error pages, the login page after a redirect), another `asset-hash` meta (a deploy), a different set of sidebar links, a `<script>` inside the new page area, a failed fetch. Not soft on purpose: links outside `[data-soft-nav]` (rows, in-page links), form posts, exports; `data-soft-nav="off"` on a link inside a region opts it out. To make another region soft, put `data-soft-nav` on its container. Fires `soft-nav:load` on `document` after each visit. |
| `resources/js/ui/session-guard.js` | Loaded on every page via `app.js`. **Log out in one tab, every other tab of the browser leaves too.** Forms marked `data-logout-form` leave a flag in `localStorage` on submit; the signed-out page that loads after the logout turns it into a `storage` event (`cucina.signed-out`), and the other tabs (hidden ones too) `location.replace()` to `meta[name=login-url]`. That meta is drawn only for signed-in users (`@auth` in `layouts/app` and `layouts/guest`), so signed-out pages never redirect. Safety net for everything the event cannot reach (expired session, logout in another browser / device, a tab that was asleep): any **401** from axios or from the notification poll (`notifications.js`, exports `leaveToLogin()`) sends the tab to the login page. A new logout form needs `data-logout-form`. Not covered: a tab that is switched to a *different account* (log in as B in tab 2 while tab 1 shows A) keeps showing A until it reloads. |
| `resources/js/ui/table-export.js` | `exportTable(table, { format: 'xlsx' | 'pdf', title })`, called from the toolbar's **Export** menu, so **every table** can be exported. **Choosing a format first asks for confirmation** (`ui/confirm-dialog.js`, "This downloads N record(s) as Excel / PDF"; it is **built like `<x-ui.modal>`** — blurred backdrop fading over 300 ms, panel scaling up from 95 % over 200 ms, title + X header, pill Cancel and primary buttons — so it matches the payment Verify / Reject / Undo confirmations; change one, change the other. Cancel has the focus, Tab stays inside, Escape / the X / the dark area cancel, focus returns to the Export button); an empty table skips the question. The texts are the `data-confirm-*` attributes of `<x-ui.table-toolbar>`. `confirmDialog({ title, text, yes, no })` returns a Promise of true / false and can be reused for other "are you sure?" prompts. Exports what the table shows: rows left by search and filters, in the current sort, **all pages**, with the columns shown; a `<th data-no-export>` (running number, Actions, pictures, proof links) is skipped. Cell text is the rendered cell without markup (badge → label, one line per order line). Built in the browser, nothing is sent to the server: `.xlsx` with `write-excel-file/universal` (bold header, frozen first row, wrapped cells, widths from content), PDF with `jspdf` + `jspdf-autotable` (landscape past 5 columns, title, record count, date, repeated header, page numbers). Both libraries load on the first export (own chunks). File name: page title + date. Needs `data-no-export` on the non-data `<th>`s and `:export-title` on `<x-ui.table-toolbar>` of a new table. |
| `resources/js/ui/row-menu.js` | `rowMenuHtml(actionsHtml, label)` wraps a row's `data-row-action` buttons in a three dots dropdown (for a table too wide for the buttons; Payments uses it in the table view, its cards keep plain buttons); `initRowMenus()` wires open / close once (outside click, Escape, scroll, resize). The panel is `position: fixed` so the table's sideways scroller cannot clip it; item styling is "Row menu" in app.css. The page's own delegated `[data-row-action]` listener still serves the clicks. |

## Signed-out pages

- **Landing page** (`GET /`, `WelcomeController`, `resources/views/welcome.blade.php`): an ink hero with the dish collage behind its right side (headline, whether ordering is open: the live session's window, else the next scheduled one, else "No session is open right now"; Create an account / Log in, or Order from the menu / Open dashboard when signed in), a "How ordering works" row of three cards, a "Ways to pay" strip built from the active payment methods, and a closing call to action for visitors. While an order session is live and/or a pre-order session is running, a **live-menu preview** card sits under the hero (up to 8 dishes each with photo, price and a "Sold out" chip, then "and N more on the full menu"; pre-order shows its minimum plates and "per plate" prices). A visitor sees *Log in to order* (a link to the menu, which bounces to login and back) and *Create an account*; a signed-in person with the permission sees *Order from the menu* / *Pre-order*; without it, no button. There is no cart on this page on purpose. The hero collage still shows names and photos only; stock numbers are never shown anywhere on this page. Light and dark, the theme switch in the top bar.
- **Log in, register, password reset** share `layouts/guest.blade.php`: from `lg` a split screen (ink brand panel on the left, form on the right), on a phone the form under a small brand header. Use `<x-guest-layout :heading="..." :subheading="...">` and an optional `<x-slot name="footer">` for the switch link ("New here? Create an account").
- **Profile page, Google Chat card** (`profile/partials/google-chat.blade.php`, Alpine inline, no script file): shown only while *Send notifications to Google Chat* is on and the Chat key is set up (`ProfileController::googleChatState`). It is a **synced indicator**: a status pill (the dot colour comes from `data-status`: green *Synced with Google Chat*, amber *Not synced yet*, red *Could not check*, grey *Checking...*) filled in after the page loads by `GET /profile/google-chat/status` (one live Google lookup, so opening Profile never waits for Google). Synced: one line (the first time, the app also sends the person its Welcome message). Not synced: the steps (install it, or open Google Chat and search the app by `GOOGLE_CHAT_APP_NAME`; then come back), **Open Google Chat** (`GOOGLE_CHAT_APP_URL`, default chat.google.com) and **Check again**. When `GOOGLE_CHAT_APP_URL` is set (the app's Marketplace listing) the button reads **Install Cucina-Feliza** and the first step says to click Install. The button opens a **how-to guide first** (`profile/partials/google-chat-guide.blade.php`, a `<x-ui.modal name="google-chat-guide">`, Alpine inline): three steps shown one at a time (click Install, confirm, come back and check: the status turns green and the Welcome message arrives), each with a small illustration that animates itself element by element (a `tick` counter on timers; the pointer glides onto Install, the dialog's Continue is pressed, the pill turns green and the Welcome bubble slides in), dots for progress, Back / Next, **Skip tutorial** (straight to the page) and, on the last step, **Go to the installation page** (a small popup window centred over the page, not a tab: Google's pages send `X-Frame-Options` so they cannot be embedded; `noopener`; closes the guide; the address is the modal's `data-url`). When the person comes back (the popup closes, the window or tab is focused again) the card and the prompt re-check the sync by themselves. With `prefers-reduced-motion` every step is shown complete and nothing moves. Without `GOOGLE_CHAT_APP_URL` there is no guide. Someone who never signed in with Google sees *Not synced yet* and is told to log out and use *Continue with Google* once (no script, no Google call).
- **Google Chat prompt after sign-in** (`components/google-chat-prompt.blade.php`, class `App\View\Components\GoogleChatPrompt`, drawn by `layouts/app.blade.php`, Alpine inline): a one-time dialog on the page a person lands on after a Google sign-in. Drawn only when `GoogleChat::shouldPrompt()` says so: they signed in with Google (`google_id`), are not synced / welcomed yet, were not checked since this login (a sign-in clears the flag, so it comes back at **every login until they are synced**), Google Chat is on and set up, and the page is not Profile (which has the full card and the one install guide). After the page loads it asks `GET /profile/google-chat/status` once: found synced just now -> an *You are all set* dialog (the Welcome was just sent); not synced -> the dialog opens with **Install :app** (the animated guide, or Google Chat itself without `GOOGLE_CHAT_APP_URL`), **Check again** (also runs when the person returns to the tab) and **Maybe later** (just closes it for the visit; nothing is stored); a Google problem shows nothing. When the guide's last step leaves for the install page the prompt comes back (event `google-chat-guide-proceeded`) so the person can press Check again.
- **Company dropdown** (`<x-company-select :companies="..." :selected="...">`, `components/company-select.blade.php`): a real `<select name="company_id" id="company_id">` styled like `<x-text-input>`, with a "Select your company" placeholder, used by the register, complete-profile and profile forms (`Company::options()`; the profile passes the person's own id so a switched-off company stays listed as "(inactive)"). With no companies it prints "No companies have been added yet. Ask the staff to add yours, then try again."
- **Company + Employee ID** (`<x-company-fields :companies :selected [:employee-id] [:autofocus]>`, `components/company-fields.blade.php`): wraps the dropdown above and an `employee_id` text box in one Alpine `x-data` (the register, complete-profile and Profile forms use it). The box is hidden, not required and disabled while the company is **Guest** (found by name in `Company::options()`); without JavaScript it simply stays visible. The server is the real check (`Company::employeeIdRules`).
- **Complete your profile** (`auth/complete-profile.blade.php`, guest layout): "One last step" after a first Google sign-up. Shows the signed-in email, first / last name (prefilled from Google) and a required Company dropdown (`<x-company-select>`), one Continue button and a Log out link in the footer. No JS module: a plain form post.
- **Continue with Google** (`<x-ui.google-button />`, under the form on `auth/login` and `auth/register`): an "or" divider and a full-width outlined pill link to `google.redirect`. It renders nothing unless `GoogleAuthController::enabled()` (both `GOOGLE_*` keys set), so no dead button. The four colours of the Google "G" are hard-coded on purpose (Google's brand rules): the one exception to "no hard-coded hex".
- **Dish collage** (`<x-ui.dish-collage :columns="$collage">`, one component for both places): on the brand panel of every signed-out page and in the **landing hero** (behind its right 62 %, faded into the ink on the left, the order ticket floating over it; without dishes the hero keeps its decorative rings), `lg` and up: three tilted columns of dish tiles scrolling **up** at their own speeds (`animate-marquee-up`, 62 / 80 / 70 s; each column holds its tiles twice and moves half its height, so the loop has no seam), with fades keeping the brand and the headline readable. Data: `Dish::showcase()` (available dishes only: name, photo URL, first type; **no prices or stock**), picked and cached 10 minutes by `Dish::collageColumns()` (called by `GuestLayout` and `WelcomeController`). Put the component in a `relative overflow-hidden` `aria-hidden` box; it fills and overflows it (it is tilted). A dish **with a photo** is a photo tile with its name; a dish **without** one is a typographic tile, and photos are spread evenly among them, so the collage looks full now and fills with photos as dishes get them. No dishes at all: the panel falls back to its three plain points. Decoration only (`aria-hidden`, `alt=""`, lazy images); `prefers-reduced-motion` stops it (`[data-collage-track]` in app.css).
- **Error pages** (`<x-error-page :code="404" />`, `components/error-page.blade.php`; `resources/views/errors/{401,403,404,405,408,413,419,429,500,502,503,504}.blade.php` are one-liners, `4xx.blade.php` / `5xx.blade.php` catch every other status through Laravel's own lookup): a centred card on the paper with the Cucina brand, the dark / light switch (restored before paint like every page), an icon, the big status number, a title and one plain sentence, then **Go to dashboard** (signed in) / **Back to home** (guest) and **Go back**, or **Try again** (reload) for the errors that can pass on their own (408, 419, 429, 5xx). A 403 also shows the sentence the app gave to `abort(403, '…')` (e.g. "Complete your profile first."), never the framework's or Spatie's technical text; an exception's own message is never shown (a 500 says nothing about SQL). It runs while the app may be broken, so the account lookup is `rescue()`d and the Vite assets (and the switch) are included only when `public/hot` or `public/build/manifest.json` exists. AJAX / JSON requests still get Laravel's JSON, not this page. To add a status, add a row to `$known` in the component and a one-line view for it (or let it use the 4xx / 5xx fallback).
- The brand mark (`<x-application-logo>`, used by the sidebar and these pages) is the **logo uploaded in System Configuration** (an `<img>` with softly rounded corners, `aspect-square rounded-lg object-cover`: a square, centred and cropped to fill the box the caller sizes; change `rounded-lg` in the component for a rounder or squarer look) or, when there is none, a serving dome on its plate filled with the current text colour. `:custom="false"` keeps the dome (the faint watermark on the dish-collage tiles). The **name** is never typed in a view: print `\App\Models\Setting::appName()` (titles, sidebar, sign in panel, footers, welcome sentence, error pages, email), not `config('app.name')` and not a literal "Cucina". Behind `Setting::brand()`: one query per web request, and it cannot throw, so an error page still renders when the database is down.

## Page modules

`scripts/harness.php` fails if a file in `resources/js/pages/` is not listed here (write each as `` `file.js` ``). **Put `<x-page-module>` inside `@push('scripts')`:** `soft-nav.js` swaps `#page-root` out of the fetched page *before* it reads the markers, so one left in the page area works on a full load and silently does nothing after a soft visit. **Every module is `const start = () => { ... }` ending in `export default start;`** (synchronous, finds its DOM by id, keeps its state inside `start`, never starts itself on `DOMContentLoaded`): `ui/soft-nav.js` starts it on every visit and removes its document / window listeners when the page is left.

| Module | View | Notes |
|---|---|---|
| `analytics.js` | `analytics/index` | Draws every `[data-chart]` (`<x-analytics.chart>`, JSON `{labels, stacked, datasets: [{label, color: 'accent' \| 1..5 \| 'other', data}]}`) with **Chart.js** (`chart.js/auto`, imported only when a chart exists, its own ~70 KB gzip chunk). Single series = the theme's `--accent`; stacked series = the `--chart-1..5` / `--chart-other` data colours of `app.css` (light and dark sets, validated for colour-blind separation on the card colours: keep the order, never add a 6th hue). Bars ≤24 px, rounded data end, a card-coloured gap between stacked segments, legend only with 2+ series, no animation under reduced motion. Redraws when `html.dark` flips; destroys charts and its observer when the page is left (`signal`). Every chart has a "Show as table" twin with the same numbers. |
| `dish-types-manager.js` | `dishes/` | The **Manage Types** drawer of the Dish Masterlist (no page of its own): a list with Edit / Delete per type and one form that creates or edits (`_method` switched POST ↔ PUT). ## Conventions

- **CRUD pattern**: page = table + drawer. Row buttons carry `data-row-action`, `data-*-url` attributes built by the controller; the module reads them. Edit loads JSON from `GET .../{id}/edit`, submit goes to `PUT`/`POST`, responses are `{status, message}` → toast.
- **Controller-built HTML**: badges and row buttons are generated in PHP (`Controller::statusBadge`, `sessionBadge`, `orderStatusBadge`, `paymentStatusBadge`). Tailwind only keeps those class names because `tailwind.config.js` scans `app/Http/Controllers/**/*.php` — do not move the class strings out of scanned paths.
- **Enlargeable images**: put `data-zoom` (+ `data-zoom-caption`) on an `<img>`, or on a proof/receipt `<a href>` (it keeps working as a link), or use `<x-ui.zoomable-image>`. Do not add `data-zoom` where a click already does something (menu dish cards open the dish modal; upload drop zones open the file picker). Escape closes only the viewer. A payment's **View proof** link is an outlined pill with a picture icon, never bare text: `<x-ui.proof-link :href="..." />` in Blade, `proofLink()` in `resources/js/ui/proof-link.js` for rows and popups built in JS (change both together).
- **Dark mode** classes (`dark:`) are required on every new colour.
- **Money is shown in pesos (`₱`)**: in Blade `₱{{ number_format($x, 2) }}`, in PHP text `OrderNotifier::money()`, in JS the `money()` helper of the module (`'₱' + toLocaleString('en-US', 2 decimals)`). Do not write a `$` amount. The PDF export swaps `₱` for "PHP " (its built-in font has no peso glyph); Excel keeps `₱`.
- Strings are wrapped in `__()` / `e()`.
- Buttons render only if the user has the permission (UI hint; the route middleware is the real gate — see security.md).
- **Sidebar tree look.** Each group (Ordering, Service, Catalog, Access) is a header with its own **icon**, a bold title and a chevron (up = open, down = folded; the click folds it, state in `html[data-nav-closed]`), and its links hang under it, indented, on a thin **vertical connector line** that starts under the header's icon (`.nav-tree` in `app.css`, 13 px links with 16 px icons); the page you are on is a **soft highlight** (gray-100 / white 10 % in dark) plus a short ink bar on the line, and there is no panel behind the active group (it was too heavy; the solid ink pill stays only for Dashboard and in the icon rail). A new group needs: a header icon, `nav-group-inner nav-tree` on its items wrapper, and its key in the `data-nav-closed` selectors in `app.css`. **Icon rail (collapsed sidebar, lg+) keeps the sidebar's open / folded state** (the group header button's `aria-expanded` is the single truth, set before paint and by `toggleGroup`): an **open** group stays open in the rail, its icon plus its links as a column of icons on a soft rounded plate, the current page the solid ink square; a **folded** group is ONE icon (solid ink when it holds the current page), instead of every link. The rail cannot fold or open a group (see below), so the state you left in the open sidebar is the state you get back. A **folded** group's links open as a **hover / keyboard-focus panel** to the right of its icon (`[data-nav-group]:hover|:focus-within .nav-group-items` in `app.css`, headed by the group name from the `data-title` attribute of `.nav-group-inner`, links with their labels, the current page soft-highlighted). The panel is `position:absolute` with no positioned ancestor before the fixed sidebar, so the scrolling list and the clipping wrapper cannot cut it, and its left padding is an invisible bridge so the hover survives the move from the icon. After a press on the collapse / expand handle no panel opens until the pointer moves again (`html.sidebar-switching`, set in `toggleSidebar`, released on the first `mousemove` after 350 ms), because the sidebar slides under an idle pointer. Sidebar width and page offset must keep the same easing / duration (`cubic-bezier(0.32,0.72,0,1)`, 300 ms) in `layouts/navigation` and `layouts/app`. Pressing a group icon in the rail does nothing (`toggleGroup` returns early), so the open sidebar's fold state is never changed from the rail. The group button keeps `aria-label` because its text is hidden there. Below lg the drawer is the full tree as before. The list scrolls with its scrollbar hidden (`.sidebar-scroll`). **Motion:** a group's links slide in from the right and out to the right (`.nav-group-items` transform + opacity + the grid-row height, 300 ms), the rail's hover panel arrives from the right too; keep it sideways, not a bottom-to-up reveal. - Nav lives in `resources/views/layouts/navigation.blade.php`; add a link there for every new page, guarded by `@can`, inside its group: **Ordering** (Menu, My Orders, Pre-Orders, My Pre-Orders; the dashboard has a tile for each of the two pre-order ones), **Service** (Order Sessions, Pre-Order Sessions, Payments; the dashboard has a Pre-Order Sessions tile too), **Catalog** (Dish Masterlist, Payment Methods), **Access** (Roles, Users); Dashboard sits above them. A group is dropped when none of its links is visible; the collapsed rail shows a thin rule instead of the title. **Each group title is a button that folds its group** (chevron turns; the links slide shut over 0.25 s by animating a grid row `1fr` to `0fr`, `.nav-group-items` / `.nav-group-inner`, and a folded group is `visibility: hidden` so Tab skips it; reduced motion turns it off). **Each group is a `.nav-group-panel`; the group that holds the current page (`data-has-active`) gets a soft gray panel and a darker title** (the page itself stays the ink pill; not in the icon rail). Folded state: the folded groups are the `data-nav-closed` attribute of `<html>` (e.g. `"catalog access"`), restored before paint from `localStorage` `cucina.nav.closed` by the script in `layouts/app.blade.php` and toggled by `toggleGroup(key)` on the shell's Alpine root; `app.css` hides `.nav-group-items` per group (one selector per key: a new group needs its key added there). The group holding the current page (`data-has-active`) is always opened on arrival, without changing what is stored; the 5rem icon rail ignores folding and shows every icon.

## Theme

A **warm gray** look. The tokens come from tokenharbor.ai (read from its stylesheet): a warm paper page and near-black ink. The **default theme has deliberately no colour accent** (the emphasis is the contrast between ink and paper), but an admin can pick a **colour theme** in System Configuration → Branding (see *Colour themes* below). Layout and shapes follow the two reference screens the redesign started from: a floating rounded sidebar (links only; the ink identity card moved into the top right account menu), big rounded dish cards with inset photos, pill search and chips, round +/− steppers.

| Token | Light | Dark | Tailwind |
|---|---|---|---|
| Page (paper) | `#f7f6f2` | `#141413` | `gray-50` / `gray-900` |
| Cards | white | `#23221e` | `bg-white` / `dark:bg-gray-800` |
| Ink (text, primary buttons) | `#17170f` | — | `ink`, `indigo-600` |
| Mist (ink's counterpart in dark) | — | `#e8e6e1` | `mist` (`mist-deep` `#d8d5cc`) |
| Muted text | `#6b6a64` | `#9a9793` | `gray-500` / `gray-400` |
| Hairline borders | ink at ~10% | white at ~9% | `gray-200` / `gray-700` |

**How it is applied.** `tailwind.config.js` *remaps* two scales instead of renaming them, so the existing classes pick the theme up unchanged: `gray` is warm neutrals, and `indigo` is the **brand**, which here is ink and grays (600 = ink, 300/400 = the light grays that carry text and rings on the dark page, 50/100 = hover and active washes). Dark mode is the **`dark` class on `<html>`** (`darkMode: 'class'` in `tailwind.config.js`): `layouts/theme-script` sets it before first paint from the saved choice (`localStorage` `cucina.theme`: `dark` / `light`) or, until someone has chosen, from the OS setting; the switch (`x-ui.theme-toggle`, `resources/js/ui/theme.js`) flips it, remembers the choice and eases the colours over 0.3 s. The switch is a round icon in the top right corner (beside the bell, in both the phone and the desktop bar) and on the login pages. Until the switch is used the page still follows the OS live. An ink button would vanish on the dark page, so `resources/css/app.css` turns every `bg-indigo-600 text-white` into `mist` with ink text there (also the pager's current page, the checkout progress bar, checkboxes and toggles).

**Colour themes (System Configuration → Branding → Colour theme).** The page (the warm gray scale, cards, text) never changes; only the **brand** does. A theme is a block of `config/themes.php` (`ink` default, then `blue`, `indigo`, `violet`, `rose`, `orange`, `amber`, `emerald`, `teal`, `sky`, `cyan`, `green`, `pink` from Tailwind and six earthy ones generated for the warm paper page: `terracotta`, `coffee`, `olive`, `sage`, `plum`, `navy`, then `red`, `fuchsia`, `purple`, `lime`, `slate`, `burgundy`, `pine`, `mustard`, `denim`, `lavender`; and sixteen **gradient** themes: `sunset`, `ocean`, `aurora`, `berry`, `ember`, `twilight`, `dusk`, `meadow`, `peach`, `glacier`, `midnight`, `mulberry`, `copper`, `citrus`, `woodland`, `rosewood`). The picker draws two rows, *Colours* and *Gradients*, split by whether the theme has a `gradient` block: an 11-step brand scale, the **accent** (solid fill of a primary action) with its text colour, a lighter **dark-mode accent** with its own text colour, and an optional `hero` (by default the accent **deepened**, `Theme::deepen()`: 45% towards black, so the big dark panels are a rich shade of the colour and never near-black). `App\Support\Theme` turns the saved one (`settings` key `theme.accent`) into CSS custom properties, printed in **every** `<head>` as `<style id="theme-vars">` by `layouts/theme-script` (signed-in layouts, sign in, welcome, public pages and error pages): `--brand-50…950` (RGB channels, e.g. `37 99 235`), `--accent`, `--accent-hover`, `--accent-on`, `--hero`; the three accent ones are redefined under `html.dark`. `tailwind.config.js` reads them as `rgb(var(--x) / <alpha-value>)`, so opacity modifiers keep working: `indigo-*` is the brand scale (links, rings, washes, chips), `bg-accent text-accent-on hover:bg-accent-hover` is the **solid highlight** (primary buttons, the current page in the menu, the card `+`, chips, progress bars, the toast tick) and `bg-hero` the big dark panels (welcome hero, sign in panel, dashboard card). `app.css` has the **built-in ink fallback** in `:where(:root)` / `:where(html.dark)` (zero specificity, so the page's own block wins in any link order). A theme's `600` is the first Tailwind shade (600–800) that keeps white text at **4.5:1** (`ThemeTest` checks every theme, light and dark). **Gradient themes** carry an optional `gradient` block (`from` / `to` for the light page, `dark_from` / `dark_to`, `hero_from` / `hero_to`); `accent` stays its first colour, so borders, rings and text keep a solid colour. `Theme::css()` then also prints `--accent-image` (and `--hero-image`, never in dark mode, where the panels are `dark:bg-gray-800`), and `app.css` lays it over the colour of every `.bg-accent` / `.bg-indigo-600` / `.bg-hero` (hover brightens, since a colour under an image cannot change). A plain theme prints `none` for them, which is also what makes a preview switch the gradient off again. **A rule that restyles such an element to a soft background (the sidebar tree's current page) must also set `background-image: none`**, or the gradient shows under dark text. Both ends must keep 4.5:1 with the button text (`ThemeTest` checks). **To add a theme** add a block to `config/themes.php`: the dropdown, the swatches, the preview and the validation read the file. **Preview:** the settings page carries the CSS of every theme in the swatches' `data-themes`; picking one (swatch, dropdown or Undo) lays it in a second `<style id="theme-preview">` so the whole page changes before Save, `settings.js` removes it when the page is left, and a save **reloads the page once** (like a new name / logo) so the `<head>` block is the saved one.

**Rules for new UI**
- Dark-only CSS that you write by hand in `app.css` must be scoped `html.dark …` (never `@media (prefers-color-scheme: dark)`: that would ignore the switch). `dark:` utilities already work.
- Primary action: `bg-indigo-600 text-white` (the theme's 600; the dark accent in dark mode, via `app.css`) or, for a pill / chip / nav item, `bg-accent text-accent-on`. Do not hard-code hex colours; use `paper`, `ink`, `mist`, `accent`, `hero` or the remapped scales. **Never write the old `bg-gray-900 text-white dark:bg-mist dark:text-ink` pair for a highlight**: it ignores the theme.
- **Every action has a border.** Ghost and text-style buttons are outlined pills: row actions (View grey, Edit darker grey, Delete red, End amber, with `mx-0.5` between them), Clear filters, the round close buttons, the stepper `−`, the top right bell and account buttons. Solid ink buttons are their own edge, and the paired pager / filter controls already carry borders. A new button must not be borderless text.
- Keep **one solid highlight** per card or row (the card `+`, the "Added to cart" chip, the active nav pill) so the eye finds it: `bg-accent text-accent-on`.
- Cards: `rounded-2xl bg-white shadow-card` (hover: `shadow-card-lift`), no heavy borders. Controls that stand alone (search, chips, steppers) are pills (`rounded-full`).
- Active navigation: the accent pill (`bg-accent text-accent-on`; ink on the default theme).
- **Add buttons** (`x-page-header`, `data-fab`): on a phone a round floating plus in the lower right (like the menu's cart; the page gets bottom padding so it never covers the last row); from `sm` it sits in the page header, upper right, as a rounded button with its label. Keep the `fixed ... sm:static` pair when editing it.
- Page titles sit directly on the paper (no header bar): `text-2xl font-bold tracking-tight`.

A table cannot round a `<tr>`, so `app.css` sets `border-collapse: separate` + `border-spacing`, puts the top / bottom border on every cell and the corners + side borders on the first / last cell; `<tbody>` backgrounds are forced transparent. Hover lights the whole row; an inactive row is muted. The search box is a pill with a magnifier inside and a `Search…` placeholder (`language.searchPlaceholder` in each page script; the label is hidden). Round pager buttons, a calm centred empty message (`td.dt-empty`). Phones start on the card view.
- **Table toolbar** (`<x-ui.table-toolbar>`, `resources/js/ui/table-toolbar.js`): the same bar on every module with a table. Left: the view tabs (Table / Card / Calendar, or none). Right: one rounded bar with **search**, a **Sort** dropdown and a **Filter** dropdown, exactly like the menu's. A page declares it in its view — `<x-ui.table-toolbar :views="['table','card']" :sorts="[[__('Name: A to Z'), 2, 'asc'], ...]">` with the filter fields as the slot (each wrapped in `<x-ui.filter-field :label="...">`; an empty slot draws no Filter button) — and calls `initTableToolbar(table)` right after creating its DataTable with `layout.topEnd: null` (DataTables' own search box is off; the toolbar's field calls `table.search()`). A sort option is `[label, column index, direction]`; the label follows the table when a header is clicked. The controls in the slot **keep their ids and their own listeners**: the helper only counts how many are away from their default (the badge) and offers *Clear filters*, which resets them and fires `change` so the page reacts (payments.js's date-range rule included). The cards and the calendar are built from the filtered rows, so they follow search, sort and filters.
  **On a phone** (modelled on the reference's mobile view) the bar stays **one row**: the search box shrinks, Sort and Filter become compact buttons after hairlines (the sort choice is clipped and hidden below 400 px, leaving the icon), and a dropdown spans the **whole bar** — the bar is its positioning parent (`absolute inset-x-0`), so it cannot run off the screen; from `sm` it hangs under its own button (`sm:relative` cell, `sm:w-80`). A new card template with a picture must carry `data-card-photo` on its picture block.

- **Analytics** (`analytics/index`, sidebar link under Dashboard with `@canany` + `Analytics::tabsFor()`, also a dashboard "Jump to" tile): one filter row (preset pills + a From / To form) above everything, then tabs **Sales / Money / Kitchen / Customers** (only those with a widget of yours; preset and tab links are soft, the custom form is a full GET). **The menu bar** is one rounded bar (like tokenharbor's model search): the search box, then a **Sort** dropdown and a **Filter** dropdown (popovers: `[data-popover]`, closed by an outside click or Escape). Sort: Default (the server's order), Price low→high / high→low, Name A→Z, Calories low→high, Most available. Filter: *In stock only*, *In my cart* (follows the cart live), price from / to, calories from / to; the badge on Filter counts those, and *Clear filters* resets them with the search box and the category. The category chips under the bar stay the quick single-select category filter. All of it runs on the dishes already on the page (`menu.js`: `shows`, `applySort`), so nothing asks the server. On a phone the search box takes the first row and Sort / Filter share the second.

**Menu dish cards are photo-first.** The photo is the card: it fills the top edge to edge (`aspect-[5/4]` on a phone, square from 520 px), zooms slowly on hover (`group-hover:scale-110`), and the text sits on a black gradient over it so white type always reads: glass category chips top left (two, then `+N`), a frosted price pill top right, the name (two lines max) and the stock line at the bottom. The stock line has a dot in front (`data-level` = `ok` green / `low` amber, 3 or fewer / `out` red); a sold-out dish turns grey with a "Sold out" label (`data-sold-out` on the card, `group-data-[sold-out=true]` variants). `menu.js` `setStock` keeps both attributes in step when stock changes. The +/− stepper sits in a strip under the photo. The dish popup's photo is taller (`h-56 sm:h-72`) to match. No photo (or a broken one): a soft gradient with an image icon.

**Motion.** Short and soft, defined once in `tailwind.config.js` (keyframes) and `app.css`:
- `animate-fade-up` — every page's `<main>` slides up as it arrives; menu cards and the search bar do the same, staggered 45 ms apart (the first 12).
- `animate-fade-in` / `animate-pop` — the image viewer opens with a fade and a small pop.
- Cards lift on hover (`hover:-translate-y-0.5`, `shadow-card-lift`); buttons and links with the `transition` utility sink slightly while pressed; sidebar icons lean toward the label under the pointer; table rows fade their hover background.
- **Add to cart:** the round cart bounces (`animate-cart-bump`) and a round copy of the dish's photo flies from its card to the cart (`flyToCart` in `menu.js`, Web Animations API; skipped when it cannot be measured).
- A **live** session badge shows a small breathing dot (`animate-live-dot`, from `span[data-status=live]::before`).
- Everything is switched off by the `prefers-reduced-motion` block in `app.css`. Fill mode is `backwards`, so a finished entrance never freezes out a hover transform.

**Mobile.** Touch targets on the menu are 44 px (`h-11 w-11`); buttons inside cards are at least 40 px; form controls are 16 px below `sm` (iOS zooms the page on anything smaller); the dish grid is one column under 520 px, then two, three, four; the round cart clears the phone's home bar (`env(safe-area-inset-bottom)`).

**DataTables loading state** (`.dt-processing` in `app.css`): the processing indicator is a round pill with ONE CSS spinner (the library's four dot <div>s are hidden because its own stylesheet is not loaded), and it is hidden while the table shows its own `td.dt-empty` row ("Loading..." / empty), so the two never overlap. **Top-right panels (bell, account menu)** are animated in AND out by CSS only (`[data-menu-panel]` in `app.css`, flipped by Alpine through `data-open`; `display` transitions with `allow-discrete`). Do not put `x-show` / `x-transition` back on them: the JS transition waits for `requestAnimationFrame`, which a hidden tab pauses, and left an open menu invisible after switching tabs (see changelog). The sidebar's collapse / expand button is a small round **handle on the right edge of the sidebar's white panel, halfway down** (about a third over the panel, the rest outside; the sidebar has 0.75rem of padding, so it is offset from the aside's own edge, and in the icon rail it is nudged out far enough not to touch the icons): expanded or in the 5rem icon rail. It is centred with a negative margin, not a transform, because the press effect in `app.css` sets `transform` on pressed buttons. Who is signed in is shown **once**, in the top right account menu's ink card (not in the sidebar): the user's **initials** in a light circle plus name, email and role; the external avatar image (`ui-avatars.com`) was removed, so a user's name is no longer sent to a third party.

**Action buttons.** Solid rounded rectangles (`rounded-xl`, soft shadow, light weight, small icon + label). Row actions are styled by `button[data-row-action=edit|view|delete|end]` in app.css (icon is a CSS mask), not by the class strings in the controllers; new row actions need a `data-row-action` value and a rule there. A row action that is a plain **link** to a page (View on Order / Pre-Order Sessions) carries `data-row-link="view"` instead, never `data-row-action` (the page scripts listen for that), and `a[data-row-link]` shares the same rules. **Wide tables:** a DataTable wider than its card scrolls sideways at every width (`.dt-layout-table` is `overflow-x: auto`); a table with many columns (Payments) adds the `dt-compact` class on its `<table>` for `px-3` cells.

**Info tip** (`<x-ui.info-tip :text>`, `components/ui/info-tip.blade.php`): a small "i" button whose bubble opens on hover / focus / click (Alpine, `position: fixed`, flips above near the bottom). System Configuration uses it for the `detail` of a field / section: a field shows its name, ONE short `hint` line under it and, only when there is more to say, the "i" with the `detail`; keep the `hint` to a few words and put anything that must always be read (a warning) in the field's `note` slot.

**Dropdowns.** **Every** `<select>` in the app is enhanced by `resources/js/ui/select-menu.js` (`autoEnhanceSelects()` from `app.js`, watching for selects added later: drawers, the DataTables page-length box): a styled button + listbox over the hidden native `<select>`, in the look of the toolbar's sort menu (rounded card, roomy rows, chosen row shaded and bold with a check, lighter shade under the pointer). The select still holds the value and fires `change`. Keep writing a plain `<select id=...>` in a page; do not listen to the custom button. Options are picked up automatically; Alpine `x-model` writes the value without an event, so dispatch a `change` after setting it from script. Looks: `data-menu-size="sm"` (smaller button), `data-menu-placement="top"` (opens upward; automatic in `.dt-length`). **The open list is drawn on `<body>` with `position: fixed`** (placed by `place()` from the button, upward when there is more room above, capped to the room it has, `data-select-list`), so no card / drawer with `overflow` clips it and the sticky Save bar cannot cover it; a new outside-click handler must treat `[data-select-list]` as inside.

**Date pickers.** **Every** `<input type="date">` is enhanced by `resources/js/ui/date-picker.js` (`autoEnhanceDatePickers()` from `app.js`, also for inputs added later), so the browser's own calendar never shows. A button styled like a dropdown (`Nov 25, 2026` + a calendar icon) stands over the hidden native input, which **stays the source of truth**: `value` is still `YYYY-MM-DD`, the form posts it, `required` / `min` / `max` / `disabled` count, and picking a day fires bubbling `input` + `change`. Writing `input.value` from a script (the instance property is wrapped), `form.reset()` and a changed `disabled` / `readonly` redraw the button. Keep writing a plain date input; do not listen to the custom button, and do not toggle classes on the input (they are replaced by `sr-only`; only its `mt-*` moves to the wrapper). The empty button reads `data-placeholder`, else the input's `aria-label` ("From" / "To" in a filter panel), else "Select date". `data-menu-size="sm"` = the compact pill (Analytics). The calendar is `w-72`, drawn on `<body>` with `position: fixed` (below the field, above it, or wherever it fits), marked `data-select-list` like a dropdown list, and **it stops click propagation**, so no "click outside" handler (table filter panel, My Orders filters) closes behind it; Escape closes only the calendar. The chosen day is `bg-accent text-accent-on` (follows the colour theme), today has a ring, days outside `min` / `max` are disabled, there is no Clear on a `required` field. The title opens a months view, then a years view; keys in the day view: arrows, Home / End, PageUp / PageDown (Shift = a year), Enter. A date can no longer be typed. **Time inputs (`type="time"`) still use the browser's own control.**

**Dish type filters are checkbox lists.** A `<select multiple data-placeholder="All dish types" data-count-label="{n} dish types">` is drawn as checkboxes that stay open while ticking; the button shows the placeholder, one or two names, or the count; the selected options are the value (`select.selectedOptions`) and a dish matches when it has ANY ticked type. Used by the Dish Masterlist filter (`#dish-type-filter`, read in `dishes.js`) and the order session dish list (`types[]`); the menu's category chips are checkboxes too (several on, "All" clears). The toolbar's badge and Clear filters understand multi selects.
