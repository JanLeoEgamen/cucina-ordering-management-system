# Security

How access is controlled today, and what is known to be weak. Update this file whenever you touch auth, permissions,
uploads, validation, sessions, secrets or config. `scripts/harness.php` fails if a permission in `Role::PERMISSIONS`
is not listed below.

## Authentication

- Laravel Breeze (session guard `web`). Login, register, password reset, email verification, password confirmation.
- **Password policy:** one rule, `Password::defaults()` set in `AppServiceProvider::boot` — at least 8 characters with a letter, a number and a special character (Laravel's `symbols()`: punctuation, symbol or space). Register, reset password and change password all use it. The sign up page shows it live (`<x-password-input meter>`: a Weak / Good / Strong bar and a checklist, hidden until the first character; `resources/js/ui/password-field.js`, same Unicode classes as the server) — a guide only, the server decides. Deliberately **no** `uncompromised()` (it would send a hash prefix to an outside service on every sign up). Passwords created by an admin in Users are still only `min:8` (S13).
- **Google sign-in** (Laravel Socialite, `GoogleAuthController`, off until `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` are set; the secret lives in `.env` only). Accounts are matched on Google's stable `sub` (`users.google_id`), then on the **verified** email, which links an existing account on its first Google sign-in (so a Google account that controls that address can enter it: acceptable because Google verified it, and refused when `email_verified` is false). An email already linked to a different `google_id`, and soft deleted accounts, are refused. New Google accounts get the **Customer** role, like `/register` (`User::giveCustomerRole()`), and an **incomplete profile**: the `profile.complete` middleware (`EnsureProfileIsComplete`, on `/dashboard` and the whole `auth` group of `web.php`) holds them on `/complete-profile` until company and names are saved (a new route in `web.php` must sit inside that group; AJAX gets 403). Registration, admin-created users, the seeder and the factory set `profile_completed_at` at once, and the migration marked every existing account complete. They also get and a random unknown password (they can set one through "Forgot your password?"). The OAuth `state` is checked by Socialite (session based); both routes are `guest` + `throttle:20,1`.
- Sessions are stored in files (`SESSION_DRIVER=file`, lifetime 120 min; they were in the database, which cost two network trips per request to a remote DB. More than one app server needs a shared store: Redis, or `database` again). Tabs of one browser share the session cookie, so logging out in one tab ends the session for all of them **on the server** at once; the other tabs' stale pages are sent to the login page by `resources/js/ui/session-guard.js` (see frontend.md), and any request they still make is refused (401 for AJAX, redirect to login otherwise).
- The opt-in `Server-Timing` header (`SERVER_TIMING=true`, default off) is sent only to people who can `view audit-logs` and carries nothing but PHP time, database time and a query count.
- **The signed-in user, their roles and permissions are served from the cache** (`AuthCache`, `AUTH_CACHE_TTL`, default 300 s). Any statement that writes `users`, `roles`, `permissions`, `model_has_roles`, `model_has_permissions` or `role_has_permissions` (Eloquent, query builder, console, queue, seeder) invalidates every cached user at once (`TableCache::watch`), so a removed role / permission or a deleted account is felt on the NEXT request (`AuthCacheTest`, with a mutation check). What it cannot see: a row edited by hand in the database, or another app server with its own file cache; there a change waits up to the TTL. Set `AUTH_CACHE_TTL=0` for several servers without a shared cache. The cached user includes its password hash and remember token (as the session user always did in memory) in `storage/framework/cache`: keep that folder as private as `storage/framework/sessions`.
- **Behind a proxy / CDN / load balancer:** set `TRUSTED_PROXIES` (`*` or a comma list of IPs / CIDRs; `bootstrap/app.php`) so the client IP, host and https come from `X-Forwarded-*`. Unset by default on purpose: trusting everyone on a server that faces the internet directly lets any client forge its IP and dodge the login throttle. Use the proxy's real address range when it is known (Cloudflare publishes its ranges); `*` is only acceptable when nothing but the proxy can reach the app.
- Passwords hashed with bcrypt (`BCRYPT_ROUNDS=12`).
- `User` does **not** implement `MustVerifyEmail`, so the `verified` middleware on `/dashboard` is currently a no-op.

## Authorisation (Spatie laravel-permission)

- Gate = `permission:<name>` middleware declared per controller (`HasMiddleware::middleware()`), **not** in routes.
  A new controller method must be added to that list or it is unprotected.
- `App\Models\Role::PERMISSIONS` is the single list of permissions. Add one there, then run
  `php artisan db:seed --class=PermissionSeeder` (idempotent; re-syncs *Super Admin*).
- **Accounts with no role get 403 everywhere.** Sign-ups get *Customer* automatically (`User::giveCustomerRole()`); accounts that registered before that have none. Run `php artisan users:give-customer-role --dry-run` to list them and then without `--dry-run` to give them *Customer* (adds only; skips accounts that already hold any role and deleted ones; refuses until `PermissionSeeder` has created the role). **Review the dry-run first:** an admin may have emptied someone's roles on purpose to block them, and this would give that person ordering access back.
- `Role::SUPER_ADMIN` ("Super Admin") holds every permission. `Role::PROTECTED` roles cannot be edited/deleted from the UI.
- `PaymentMethod::PROTECTED` ("Cash on Pick up", the only cash method) cannot be edited/deleted (matched by name; the table feed also hides their buttons).
- Row-level rule: only the creator of an order session can end it (`OrderSessionController::canEnd`), on top of `end order-sessions`.
- Customer cancel: `POST /my-orders/{id}/cancel` (`create orders`, throttled 10 / minute) lets a customer cancel only their OWN order (anyone else's answers 404), only while the System Configuration switch `orders.customer_cancel` is on (off by default, read on every request, so switching it off stops the next cancel; 403 otherwise), only while the order is pending and its payment is **not verified** (then staff must undo it first). The order row is locked and judged again inside the transaction, so a double tap gives the stock back once. A customer's cancel never stamps them as the payment's reviewer. The switch is behind `edit settings`.
- Pre-ordering: `POST /pre-orders` is throttled (10/min per user), takes a per-customer cache lock and an idempotency key, prices every line from the database at the time of the order (the page's prices are only compared, never trusted), and refuses a dish that is not on the live session's pre-order menu. The size of an order is bounded server-side by the limits in System Configuration (`edit settings`): not under the minimum, not over the maximum, both read fresh on every order. The proof of payment is an image ≤2 MB stored on the `public` disk and deleted when the order is not written. `My Pre-Orders` reads only `user_id = the signed-in user`.
- Row-level rule: only the creator of a pre-order session can end it (`PreOrderSessionController::canEnd`), on top of `end pre-order-sessions`. A pre-order session with orders cannot be deleted. The pre-order session title is typed by staff and printed in the table feed: DataTables escapes it (it is not a raw column).
- Users cannot delete their own account via `/users/{id}`.
- Table-cell action buttons are rendered server-side only if the user holds the permission (UI hint only — the route middleware is the real gate).

## Audit trail

`App\Http\Middleware\AuditTrail` sits in the `web` group, so **every route is covered, present and future**; sign in / out / failed sign in come from Laravel's auth events (`App\Listeners\AuditAuthEvents`), so Breeze, Google sign-in and any later way in are covered the same. Entries go to `audit_logs` (see [database.md](database.md)).

- **What is written** (one row each): every **change** (POST / PUT / PATCH / DELETE) of a signed-in person, whatever the result — success, a rule that said no (`failed`, with the app's message), a 403 / 401 (`denied`), a 5xx (`error`) — with who (copied: name, email), what (`users.destroy` → "Deleted a user"), which record (`users`, id, label copied *before* the request runs, so a deleted record is still named), **what changed** (`{field: [before, after]}` for the record the route names, read before and after), what was sent (the input), IP and browser. **Page views are off by default** (`AUDIT_LOG_VIEWS=true` logs every full page load, never table feeds or polls): navigation is the bulk of the rows and says little, and sign in / out, changes and refusals do not depend on it. **Sign in, sign out, failed sign in** (the address typed, never the password), **lockout**, **registration**, **password reset**. Taking the log out as CSV, and the prune command, are entries too.
- **What is never written:** passwords, tokens, secrets (any input field whose name contains `password`, `token`, `secret`, `pin`, `card`, `cvv` is stored as `[hidden]`), the `users.password` / `remember_token` / `google_id` columns, uploads (only their file name), the query string (an OAuth `code=` or reset token can sit in it), guests' requests.
- **Append only:** the model has `record()` and `prune()` only; no route updates or deletes an entry (a test asserts 405). The only delete is `php artisan audit:prune` (scheduled daily, `AUDIT_RETENTION_DAYS`, default 365, `0` = keep for ever), and each run that deletes something writes a `system` entry.
- **It never gets in the way:** every write is inside `rescue()`: a failure is logged and the person's request goes on (tested by dropping the table mid-request). `AUDIT_ENABLED=false` switches it off.
- **Personal data:** the log holds names, emails, IPs and what people typed. Treat it like the users table: only `view audit-logs` holders read it, set a retention you can justify, and exclude it from any public export. CSV cells starting with `= + - @` are prefixed with `'` (a name typed as a formula cannot run in Excel).
- **Adding a route:** nothing to do, it is logged under its route name (or `METHOD path` when unnamed). To get a proper sentence add it to `config/audit.php` `actions`; to get the record's label and a before / after diff add its route prefix to `subjects` (`{id}` must be the route parameter).

## Input handling

- All writes validate with `$request->validate()` inside the controller; ids in paths are `whereNumber`.
- DB access uses the query builder with bindings (no string-concatenated SQL). The two `DB::raw()` stock updates in
  `SessionDish` cast the quantity to `(int)`.
- Output: Blade escapes by default. Controller-built HTML (badges, row buttons) must wrap every dynamic value in `e()`.
- Errors: every HTTP error renders the themed `<x-error-page>` (`resources/views/errors/`). It prints fixed wording per status and, for a 403 only, the message an `abort(403, '…')` call chose (escaped; the framework's and Spatie's own wording is suppressed). Exception messages of a 500 (SQL, paths) are never printed; with `APP_DEBUG=false` (production) a stack trace never reaches the browser. Keep `APP_DEBUG=false` outside local development.
- **Dish import (Excel).** `POST /dishes/import` needs `create dishes` (so does the template download) and is throttled 20 / minute (a check and a confirm are two requests): it parses a file from outside, the heaviest thing the page does. **`mode=update` (changing dishes that exist) also needs `edit dishes`, and `mode=replace` (the file becomes the whole menu: dishes it leaves out are soft-deleted) needs `edit dishes` AND `delete dishes`**, checked in the action (403 without them, also for a `preview`); a replace file with no dish row is refused so the menu cannot be emptied by accident, and the drawer only offers the option to people who hold both permissions; the filled-in template (`?current=1`) discloses the whole menu, so it needs `view dishes` too. A check (`preview=1`) stores nothing and keeps no file. In the template, dish and type names are written as **text cells** (`setCellValueExplicit`), never as formulas, so a dish called `=1+1` cannot run anything when staff open the file (formula injection). Rules: extension `.xlsx` and 2 MB (`extensions:xlsx`, `max:2048`; the real check is that PhpSpreadsheet's `Xlsx` reader can open it, else 422), at most 2,000 data rows and a single column letter (`A`-`Z`), the file is read in **data-only** mode and the cells are taken **without calculating formulas** (a formula in a file from outside, e.g. `WEBSERVICE`, must never run: a cell starting with `=` is refused with its row number), the file is read from PHP's upload temp path and never stored. Values are validated by Laravel rules like the dish form (name 255, price 0-99,999,999.99, calories whole number) and written only through the query builder (no raw SQL), all rows in one transaction after the whole file passed. **New dish types:** a name on the Dish Types sheet that is not taken is created, but only for a person who also holds `create dish-types` (checked with `$request->user()->can()` and passed to the importer; without it the file is refused with the row named, so `create dishes` alone cannot be used to add types). Names are matched against every type including deleted ones, like the Dish Types form's unique rule, and types and dishes are written in the same transaction as the dishes (a refused file creates neither). Library: `phpoffice/phpspreadsheet` (keep it updated: `composer audit`).
- Uploads: `image` + `mimes` allow-list, 2 MB cap, stored with a generated name (`store()`), never the client file name. The **app logo** (System Configuration, `edit settings`) follows the same rule and additionally **refuses SVG and GIF** (`mimes:jpeg,png,jpg,webp`): an SVG opened on its own URL runs its scripts on this site's origin (stored XSS by anyone who can edit settings). The app name is plain text, escaped by Blade everywhere it is printed. The **colour theme** (`theme_accent`, `edit settings`) is validated with `Rule::in` against the keys of `config/themes.php`, and the CSS printed in every `<head>` (`<style id="theme-vars">`, `{!! !!}`) is built **only** from the colours in that file turned into `r g b` numbers (`Theme::channels()` returns `0 0 0` for anything that is not `#rrggbb`), never from a request or stored value, so an admin cannot inject CSS or script through it.
- Support page: `GET /support` is **public by design** (visitors who cannot sign in need it; no `auth`, no permission, no form: it only shows contact details, so there is nothing to spam). What it shows is written by whoever holds `edit settings` (System Configuration → Support): the help text goes through `App\Support\SafeMarkdown::render()` exactly like the legal pages (raw HTML escaped, unsafe links dropped), the email is validated (`email`, ≤ 120) and printed in `mailto:`, the phone is limited to digits, spaces and `+ ( ) - .` (≤ 40) and its `tel:` link is rebuilt from digits and `+` only, the hours (≤ 120) are printed escaped. Nothing about a visitor is stored. The built-in FAQ (`resources/support/default.md`) names the real pages and flows: **update it when a menu label or a flow it describes changes**.
- Legal pages: `GET /privacy-policy` and `GET /terms-of-service` are **public by design** (the sign in / sign up pages link to them; no `auth`, no permission). Their text is written by whoever holds `edit settings` (System Configuration → Privacy policy / Terms of service), so it is treated as untrusted markup: `App\Support\SafeMarkdown::render()` (shared with the support page) converts it with `Str::markdown(... 'html_input' => 'escape', 'allow_unsafe_links' => false)`, so raw HTML (`<script>`, `<img onerror>`) is printed as text and `javascript:` links are dropped, and the result is the only value the view prints unescaped. `{app_name}` is substituted AFTER the conversion and escaped. The contact email is validated (`email`, ≤ 120) and printed escaped in a `mailto:` link. No new permission. The audit trail stores the text of such a save cut to 300 characters like any long field. The built-in texts (`resources/legal/privacy-policy.md`, `resources/legal/terms-of-service.md`) describe what the app collects and the rules the app enforces (payment, pick up, cancelling): **re-read them whenever a feature starts collecting something new or a rule changes**, and have them checked by whoever is responsible for data protection and for the business where you operate; they are starting points, not legal advice.
- Stock: reservation is a single conditional `UPDATE` inside a transaction (no oversell race), in a fixed line order with deadlock retry.
- Concurrency on orders: `POST /orders` holds a per-customer cache lock (409 on a parallel request) and honours an `idempotency_key`
  (replays return the first receipt); Complete / Cancel / Verify / Reject lock the order row and re-check inside the transaction
  (no double release of stock, no verified payment on a cancelled order). The cache driver must support locks (`database`, `redis`, `array` do).
- `payment_method_id` must be an **active** method (a switched-off one is refused). A database error is never shown to the customer
  (`StockRanOutException` is its own type; the old `catch (RuntimeException)` also caught `PDOException`).
- `GET /menu/stock` exposes only stock numbers and prices (and the ala carte switch + rice price), behind `view menu`.
- **Ala carte (a plate without rice).** No new permission: the switch and the rice price are System Configuration (`edit settings`), "Comes with rice" is a field of the dish (`create` / `edit dishes`), ordering is `create orders` / `create pre-orders`. The money rule is the server's: a customer can only say HOW MANY plates of a dish go without rice (`ala_carte[id]`); there is no price field to tamper with (a posted `unit_price` / `total_amount` is ignored, `AlaCarteTest`). `AlaCarte::judge()` re-checks everything as it is **now** (mode covers this kind of order, rice price above 0, the dish comes with rice and costs more than the rice, the count is not above the quantity, the rice price the cart showed is still the price) and refuses with `AlaCarteRefusedException` (a dedicated type whose message is safe to show; never a `RuntimeException` catch), writing nothing. The reduced `unit_price` is copied onto the line, so changing the rice price or the dish later never rewrites a placed order, and the discount percent applies to the subtotal that already has the deduction.
- Notifications (`/notifications*`) have **no permission on purpose**, like the profile: every query is scoped by `user_id = auth id`, an id
  that is not yours answers 404, and *open* only follows a local path (a url not starting with a single `/` is ignored: no open redirect).
  The text is written by the app (order number, dish name, customer name, the reviewer's rejection reason), always printed escaped.
  **New dish alerts** (System Configuration → Notifications, behind `edit settings`, setting `notifications.new_dish_watchers`): the picked users get "New dish added" (name, price, types, who added it) from the Add Dish form. It carries nothing about customers or orders; its link opens the Dish Masterlist only for a person with `view dishes`. Email and Google Chat are two switches of their own (`notifications.new_dish_email`, `notifications.new_dish_google_chat`, off by default, same `edit settings` gate), so the order notification switches never send it. No new permission.
  **Privacy:** a watcher (System Configuration → Notifications, behind `edit settings`) receives every customer's name, order total,
  payment method and rejection reasons, so pick them like you would grant `view orders` + `view payments`; a notification's link is
  only set when the watcher holds the permission for the page it opens. The poll is not throttled (a count and an indexed range read).
  **Google Chat copy** (System Configuration → Notifications → *Send notifications to Google Chat*, behind `edit settings`, **off by default**): the same people and words as the bell, sent as a direct message by a Chat app (`App\Support\GoogleChat`, job `SendGoogleChatMessages`, `tries = 1`). **The text of every notification leaves the server for Google** (customer names, order numbers, totals, and the dishes of the order in the message), like email does. The **service account key** is a file whose path is `GOOGLE_CHAT_CREDENTIALS` in `.env` (never in the database, the repo or the log; only `client_email` / `private_key` are read, and a log line carries a status code, never the key or the message). The app signs in with the self-granted `chat.bot` scope only (no admin-approved `chat.app.*` scope): it can only write to spaces it is in, i.e. to people who added the app themselves. People are found by `users.google_id`; accounts without one are skipped. The Profile page's **synced indicator** (`GET /profile/google-chat/status`, `auth`, throttled 20 / minute, no permission) only ever looks at, and sends the Welcome to, the caller's own Google account; the status call never returns the server's setup (service account, key path, Google's error text) to a customer. **Email copy** (System Configuration → Notifications → *Send notifications by email*, behind `edit settings`, **off by default**): the same text goes to the account email of everyone who got the in-app notification, so the privacy note above now reaches mailboxes the app does not control (a watcher's address is a place customer names and totals leave the system). The mail credentials stay in `.env` (`MAIL_*`), never in the settings table. The page warns when the mailer is `log` / `array` (emails are only recorded). Sent text is escaped by the markdown mail template; failures are logged with the user id, not the address.
- Fixing a rejected payment (`POST /my-orders/{id}/payment/proof|cash`) is behind `create orders` (no new permission) and **owner-only**: an
  order that is not the caller's answers 404, like a missing one. The new proof goes through the same upload rules as at checkout (`image`,
  `mimes`, 2 MB, generated name); it is deleted again when the request is refused, and the replaced picture is deleted when it succeeds.
  The state change happens under the order's row lock. Throttled 10 / minute per user. A customer can only move their own payment from
  `rejected` back to `pending`; only staff with `verify payments` can ever make it `verified`.
- **Discounts and the customer's ID.** The ID a customer uploads for a discount (a PWD or Senior Citizen card) is personal data, so it is **never on the public disk**: `OrderDiscount::storeProof()` writes it to the private `local` disk (`storage/app/private/discount-proofs/`, `pre-order-discount-proofs/`), the row keeps only that path (never sent out: `Controller::orderRow()` swaps it for a guarded URL and the customer's popup has no proof key at all), and it is served only by `GET /orders/{id}/discount-proof` to the order's own customer or to staff holding `review discounts` / `view orders` (everyone else, and an order with no ID, get 404; `Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff`). Upload rules: raster pictures only (`image` + `mimes:jpeg,png,jpg,webp`, 2 MB, generated name; **no SVG**, it would run scripts on this origin), deleted again when the order is not written. **The server never trusts the client's numbers:** it reads the percent and the validity of the discount at the moment of ordering (`Discount::usable()`: live, on, inside its dates, and offered for that kind of order by `discount_mode`) and does the math itself; a percent that moved since the cart was drawn is refused like a price change. A decision (`review discounts`) locks the order row and re-checks inside the transaction, so two reviewers or a Cancel cannot both win; a pending discount blocks verifying the payment, completing and announcing the order, and a rejection puts the full price back and sends a bank / e-wallet payment back to its customer. A rejected discount can be tried again with a new ID (`POST /my-orders/{id}/discount/proof`, `create orders`, **owner-only**, throttled 10 / minute, same raster-only upload rules, locked and re-checked inside the transaction): it is refused once the payment was verified (that was verified at the full price) and while discounts are switched off, and the replaced ID file is deleted, so a customer cannot pile up pictures. Uploaded IDs are **not deleted** when an order is cancelled or completed (they are evidence for the decision); plan a retention policy for them before go-live (see known-issues D1).
- CSRF: Laravel `web` middleware on all routes; axios attaches the token.

## Secrets & config

- `.env` is git-ignored; `.env.example` is committed and must contain **no real secrets**.
- `APP_KEY` is generated per environment (`php artisan key:generate`).
- Timezone `APP_TIMEZONE=Asia/Manila` — session start/end times are compared in this zone.
