Browser: `orders.js` / `payments.js` are `serverSide` (filters sent from `ajax.data`, running number continues over pages, cards = current page), search waits 350 ms, and **Export** (`table-export.js`) fetches every matching row from the server 500 at a time (up to 5,000, with a toast beyond) and renders it through a hidden DataTable built from the page's own columns. New migration `2026_11_24_100000` (indexes on `orders` date / statuses, `payments` date / status, `order_items.order_id` where missing: MySQL already had the last one, SQLite did not and a dish search took 3 s). - error: **`php artisan migrate:fresh --seed` failed** (`no such table: cache`, then `FOREIGN KEY constraint failed` in `PermissionSeeder`). Root cause: my `TableCache` write listener (the previous perf commit) wrote to the cache INSIDE the "statement executed" event. With `CACHE_STORE=database` that meant (1) writing to the `cache` table while `migrate:fresh` was still building the schema (throws), and (2) on SQLite an extra insert between a row's `insertGetId` and the read of its id, so the Super Admin role got the cache row's id and the pivot insert broke a foreign key (MySQL's `LAST_INSERT_ID()` is not changed by a table without an auto-increment column, so MySQL only hit (1)). Fix: the listener only notes the table written; the versions are bumped right before the next cached read and again at commit / request end / queue job end (`TableCache::flush()` / `settle()`, errors swallowed), `cache`, `sessions`, `jobs`, `migrations`, `audit_logs` and `user_notifications` are ignored, and a finished migration flushes the whole cache (a file cache survived `migrate:fresh` and would have served the old rows). Verified with `migrate:fresh --seed` on a scratch SQLite file with both `CACHE_STORE=database` and `file`. Tests in `TableCacheTest`. CLAUDE.md Gotchas.
