# Cucina Ordering Management System

Laravel 12 / PHP 8.2 monolith (Blade + Alpine + Tailwind 3 + Vite) for session-based food ordering: staff publish timed
*order sessions* with limited dish stock; customers order from the live menu and pay cash-on-pickup or bank/e-wallet.
Auth = Breeze; permissions = spatie/laravel-permission. Overview and conventions: @docs/architecture.md

## Working loop (mandatory)

@docs/harness.md

Short form: **understand → plan → implement → verify → sync docs → report.** A task is not done until
`php scripts/harness.php` is green and every doc whose trigger fired (table in harness.md step 5) is updated.
**On every new feature, fix, error resolved, schema/permission change: update the docs automatically, in the same change,
and add a line to `docs/changelog.md`.** Do not wait to be asked.

php scripts/harness.php             # docs-drift check + tests;  --docs = drift only
php artisan perf:check            # ON THE SERVER: times a DB commit, a cache write and a file write (own scratch table, dropped)

npm run build                       # must pass after frontend changes

Shell is PowerShell on Windows (Git Bash also available). `php` and `npm` are on PATH.

## Rules that are easy to get wrong

- Models are **static query-builder classes**, not Eloquent relations. Match the existing model you are editing.
- Authorisation is in each controller's `middleware()` (`permission:<name>`). New action ⇒ new middleware entry ⇒ 403 test.
- New permission ⇒ add to `Role::PERMISSIONS`, rerun `PermissionSeeder`, update security.md.
- Reuse `Controller::successResponse()/errorResponse()` (`{status,message}`); validation errors stay Laravel-default 422.
- Escape with `e()` every dynamic value in controller-built HTML. Keep badge class strings under `app/Http/Controllers/**` (Tailwind scans it).
- Colours come from the theme (docs/frontend.md, Theme): primary buttons are `bg-indigo-600 text-white` (it is ink; mist in dark mode), `gray` is the warm paper scale. No colour accent and no hard-coded hex. Motion stays short and must respect reduced motion.
- Dark mode is the `dark` class on `<html>` (a switch, default = OS). Hand-written dark-only CSS must be `html.dark …`, not `@media (prefers-color-scheme)`.
- Soft deletes everywhere: filter `deleted_at IS NULL`. Never edit an applied migration.
- Stock changes only via `SessionDish::reserve()/release()` inside a DB transaction.
- Code style is hand-formatted (`' . '` concatenation). **Do not run Pint repo-wide.**
- Never commit `.env`, real credentials, or uploaded files. Do not commit unless asked.

## Gotchas (append one line per trap you hit)

- `User` is not `MustVerifyEmail`, so the `verified` middleware does nothing.
- Self-registered users (form or Google) get the **Customer** role through `User::giveCustomerRole()` (menu + ordering only). If `PermissionSeeder` has not run the role does not exist and they stay role-less (403 on the menu), so seed before opening registration. Accounts that registered before this change have no role: run `php artisan users:give-customer-role --dry-run`, then without the flag (it skips anyone who already has a role).
- Payment rules depend on the method: Cash on Pick up is verified by completing its order (no manual verify/reject); other methods are verified first, then completed. Cancelling an order releases its stock and is refused while its payment is verified (undo that first). A *rejection* does NOT release the stock: the customer can resend a proof or switch to cash (`my-orders.payment.*`), so the plates stay held until staff cancel.
- `#delete-modal-*` / `#save-modal-*` exist once per page and `dishes.js` owns them: a second page module on the same view (the Manage Types drawer) must not bind them — it confirms deletes inline and tags its buttons `data-type-action`.
- Windows: running `php artisan test` while the dev server is up can fail with "rename(...storage/framework/views/...tmp) Access is denied"; run the tests with `VIEW_COMPILED_PATH` pointing at another folder.
- Users have `first_name` + `last_name`, **no `name` column**: read `$user->name` (accessor) in PHP and use `User::fullNameSql($alias)` in query builder selects; never select `users.name`.
- Order rows are decorated in ONE place, `Controller::orderRow()` (badges, proof URL, action URLs by permission); the session page and the Orders page both use it with the shared `<x-ui.order-popup>` / `order-popup.js`. Do not copy that logic into a page.
- A new table needs `initTableToolbar(table)`, `data-no-export` on its non-data `<th>` (#, Actions, pictures) and `:export-title` on `<x-ui.table-toolbar>`: that is all the Excel / PDF export needs.
- `tests/TestCase.php` comment says 16 permissions; real count is `count(Role::PERMISSIONS)`.
- `PDOException` / `QueryException` **are** `RuntimeException`s: never `catch (RuntimeException)` around a transaction to report a business rule (it shows SQL to the customer). Throw and catch a dedicated exception (`StockRanOutException`).
- Anything that changes an order's state (complete, cancel, verify/reject) must start with `Order::lockedStatus($id)` inside `DB::transaction` and re-check there: checks done before the transaction are racy (a double Cancel gave stock back twice).
- Reserve several dishes in ascending `session_dish_id` order, or two crosswise carts deadlock MySQL. `SessionDish::stockOfSession()` is what the menu polls; a dish missing from it means "sold out".
- **My Orders and My Pre-Orders are paginated (10 a page): never link to an order with `#order-ID` alone**, the card may be on another page. Link `route('my-orders.index', ['order' => $id], false) . '#order-' . $id` (`?order=ID` redirects to the right page; `NotificationController::open` upgrades old `#order-ID` links). A customer's order popup data comes from `Controller::customerOrderPopup()` and must never gain a staff field or an action URL: the popup shows or hides rows by the presence of keys.
- Notifications go through `App\Support\OrderNotifier`, called **after** the event's transaction has committed (never inside it). It pushes ONE queued job (`DeliverNotification`, queue `notifications`) inside `rescue()`; the worker writes everyone told by ONE bulk insert. Do not add a per-recipient query or a per-recipient job. The bell polls (AJAX, ~1 s); there is deliberately no websocket / Reverb. Without a worker (`queue:work --queue=notifications,default`) nobody is notified. A new event = a constant + a method + two texts (customer / staff) + a `NotificationTest` case.
- Windows is case-insensitive: `__('Pagination')` (also `Auth`, `Passwords`, `Validation`) resolves to Laravel's `pagination.php` language file and returns an **array**, which crashes `{{ }}` with "htmlspecialchars(): Argument #1 must be of type string, array given". Never use a label that equals a language file name; it works on Linux, which hides the bug.
- The table is `user_notifications`, not `notifications` (Laravel's own uuid/morph table, which the `User` model's `Notifiable` trait would use). Run `php artisan migrate` after pulling.
- `Job::dispatch()` returns a `PendingDispatch` that only fires in its destructor, i.e. **after** a surrounding `rescue()` has returned: dispatch with `Bus::dispatch(new Job(...))` inside `rescue()` or a push failure escapes into the request.
- Windows: **PHP without OPcache makes every local request 300 ms+ and `artisan serve` (one request at a time) queues parallel ones**, so a table feed shows 1-2 s in DevTools although the endpoint takes ~5 ms. Check `php -m` lists `Zend OPcache`; if not, enable `zend_extension=opcache` + `opcache.enable=1` in the php.ini `php --ini` reports and restart `composer dev`. Profile the app with an in-process request before touching code.
- Windows: a stray lowercase `composer` environment variable (pointing at another profile's `vendor\bin`) makes `composer require` fail with "file_put_contents(...vendor\bin): Permission denied"; `unset composer` / `Remove-Item Env:composer` in that shell.
- `users.email` is unique **including soft deleted rows**: any code that creates a user from an outside email (Google sign-in) must look with `User::withTrashed()` and refuse a deleted account, or the insert throws a duplicate-key error.
- The app's **name and logo are settings** (System Configuration → Branding), not code: print `\App\Models\Setting::appName()` and use `<x-application-logo>`; never type "Cucina" in a view and never use `config('app.name')` (it is `.env`'s "Laravel"; only the email job overwrites it from the setting). `Setting::brand()` must stay non-throwing (error pages call it) and logo uploads must stay raster-only (no SVG: stored XSS).
- A new route behind `auth` must live inside the `['auth', 'profile.complete']` group in `routes/web.php` (or carry that middleware), or a Google sign-up that has not completed its profile can reach it. Tests that need an unfinished user use `User::factory()->profileIncomplete()`; the plain factory user is complete.
- A user's company is a **record**, not text: `users.company_id` → `companies` (the Companies page, `view|create|edit|delete companies`), picked from `<x-company-select>` and validated with `Company::rules($currentId)` (required; active + live; the person's own switched-off company stays valid). There is no `users.company` column any more: never read or write it. `CompanySeeder` (in `DatabaseSeeder`) seeds Bounty Fresh Inc., Bounty Plus Inc. and Guest (`Company::PROTECTED`: locked by name, never editable or deletable); without any company register shows an empty dropdown, so an existing database that skipped it needs `db:seed --class=CompanySeeder` (or staff adding one). Run `php artisan migrate` (it converts the old typed names) and `db:seed --class=PermissionSeeder` (new permissions) after pulling. `UserFactory` creates a company per user: pass `company_id` when a test needs a particular one.
- The audit trail is ONE middleware (`AuditTrail`, in the `web` group) plus the auth events: **do not add audit calls to controllers**. A new `{id}` resource needs its route prefix in `config/audit.php` `subjects` (else its entries have no record label / before-after diff), and a readable name in `actions`. Read `config('audit.actions')[$name]`, never `config('audit.actions.' . $name)`: route names contain dots, which config reads as nesting. `audit_logs` is append only: never add an update / delete route or method for it (prune is the only delete). After pulling, run `migrate` and `db:seed --class=PermissionSeeder` (new permission `view audit-logs`).
- The feature once called **bulk orders** is **Pre-orders** (`PreOrder*` models, `pre_*` tables, `pre-order-*` routes / permissions, `PRE-` order numbers). Old changelog entries and the four `create_bulk_*` migrations still say "bulk" on purpose (history / applied migrations); a rename migration (`2026_11_19_210000`) moved the data. Never type "bulk" for it in new code or docs; "bulk insert" (notifications) is unrelated.
- A controller that REFUSES with a redirect must flash an error (`withErrors(...)`), not only a status: the audit trail reads "redirected back with errors" as `failed`, a bare redirect is logged as a success.
- Google Chat copy: same rules as email (`OrderNotifier::copies()` runs AFTER `insertMany()`, inside `rescue()`; `SendGoogleChatMessages` stays `tries = 1`). Only people with `users.google_id` who added the Chat app can be messaged, and `GoogleChat::message()` must never throw. Messages are plain text (`GoogleChat::format`; never a card: it shows as "sent an attachment" in the preview); `mailRow()` carries `order_id` + `type` for them (the email job ignores both). The key is a FILE named in `GOOGLE_CHAT_CREDENTIALS`: never put it in the DB, the repo, a log or a test fixture (the test generates a throwaway one). The Google Chat prompt after sign-in (`<x-google-chat-prompt>` in `layouts/app.blade.php`) and the Profile card each include the install guide, whose modal is named `google-chat-guide`: never draw both on one page (the prompt skips the `profile.edit` route for that reason), or one click opens two. The first message a person gets in Google Chat is the Welcome (`GoogleChat::welcome`, marked in `users.google_chat_welcomed_at`): the job and the Profile status both go through it, so never send a person a notification card without it. The `google_id` = Chat user id equivalence is assumed from Google's docs, unverified against a real Workspace.
- Windows: PHP ships **without a CA bundle** (`curl.cainfo` / `openssl.cafile` empty in php.ini), so every HTTPS call to Google fails with "cURL error 60: unable to get local issuer certificate" (Google Chat DMs are then silently skipped; only a log warning). Download https://curl.se/ca/cacert.pem, set `curl.cainfo` and `openssl.cafile` to it in the php.ini `php --ini` reports (**forward slashes**: `C:/php/cacert.pem`, a backslash path gets mangled), restart `composer dev`.
- Notification emails: `OrderNotifier::email()` must stay AFTER `insertMany()` and inside `rescue()`, and `SendNotificationEmails` must stay `tries = 1`. A throw in either makes `DeliverNotification` retry (bell rows written twice) or mails everyone twice. The switch is `Setting::emailNotifications()` (default off); new notification events get email for free because they build their rows through `mailRow()`.
- The **legal pages** (`/privacy-policy`, `/terms-of-service`) are admin-written Markdown settings (`privacy_policy.content`, `terms_of_service.content`), printed unescaped by `legal.blade.php` ONLY after `App\Support\SafeMarkdown::render()` (`html_input => escape`, `allow_unsafe_links => false`): never print them any other way, and never raise `Setting::LEGAL_MAX_LENGTH` past what fits the TEXT column (15,000 characters x 4 bytes). The form textareas are prefilled with the built-in text (`resources/legal/<page>.md`), so `Setting::setLegalPage()` must keep storing "equal to built-in" as empty and writing only changed values ("Last updated" is the rows' `updated_at`). Both routes stay outside `auth`. Update the built-in texts when the app starts collecting something new or a rule changes.
- The public **Support page** (`/support`) is settings too (`support.*`, Markdown help text via `SafeMarkdown` + email / phone / hours), outside `auth`, and has no form on purpose (not a ticket system). Its built-in FAQ (`resources/support/default.md`) quotes real menu labels and flows (My Orders, Cancel order, Forgot your password?, Profile, Delete Account): update it when one of them changes. Public text pages use `<x-public-page>`.
- **Sidebar navigation is soft** (`resources/js/ui/soft-nav.js`): only `#page-root` is swapped, the page is never reloaded, so a page module must be `const start = () => {...}; export default start;` (never `DOMContentLoaded`, never module level state), is named in its view with `<x-page-module name="..." />` (never `@vite` of a page file: it would not run on a soft visit), and may add `document` / `window` listeners only synchronously inside `start()` (they are removed when the page is left). A timer, observer or something appended to `body` must stop / clean up by itself (see `menu.js`, `row-menu.js`). Keep `<script>` tags out of the page area (the router falls back to a full load). Only `[data-soft-nav]` regions are soft. No automated browser test covers it: click through the sidebar after changing a page script.
- `resources/js/pages/settings.js` tracks every control that has an `id` for its "Edited / Was / Undo" indicator and **throws at start-up on a control type it does not know** (a `<select>` has no `defaultValue`), which leaves the form without its submit handler: the browser then posts it natively and shows the raw JSON reply. After adding any new kind of field to System Configuration, click Save once in the browser; `snapshot()` must handle it.
- **Discounts** (`Discount`, Discounts page, switch in System Configuration → Discounts = `Setting::discountsFor('orders'|'pre_orders')`): the customer's pick is judged and calculated **only on the server** by `App\Support\OrderDiscount::resolve()` (the JS just previews); an order keeps a **copy** (`discount_name`, `discount_percent`, `subtotal_amount`, `discount_amount`) and `total_amount` / `payments.amount` are the discounted total, so never recompute an old order from the `discounts` row. `orders.discount_status = pending` blocks verify payment, complete and announce-ready (`Controller::orderRow` hides the URLs, `PaymentController::decide`, `OrderController::complete|ready` and `Order::announceReady` refuse): any **new** way to verify / complete / announce an order must check it too. A rejection changes the order's total, so it moves the payment's amount and sends a paid-in-advance payment back in the same transaction (`OrderDiscountController::reject`); the customer's retry after a rejection (`OrderController::resubmitDiscountProof`) does the opposite move in the same way (total and payment amount back to the discounted figures, a payment still waiting at the full price sent back) and is refused once the payment was verified. The customer's ID lives on the **private** `local` disk: never `Storage::disk('public')`, never put `discount_proof` (the path) in a feed row or the customer popup (`orderRow` swaps it for the guarded `orders.discount.proof` URL), and keep uploads raster-only. Tests that place an order with a discount need `Storage::fake('local')`. Pre-orders store the same columns, but staff cannot decide a pre-order's discount until the pre-order lifecycle exists (known-issues D2). After pulling run `php artisan migrate` and `php artisan db:seed --class=PermissionSeeder` (`review discounts`).
- A **running queue worker keeps the old code**: after adding or changing a job kind, `OrderNotifier` or a notification text, run `php artisan queue:restart` (it makes a hand-started `queue:work` EXIT and nothing brings it back: start it again; under Supervisor it respawns, and `composer dev` uses `queue:listen`, which reloads code per job anyway), or the new event fails in the worker (`failed_jobs`) while the request looks fine and nobody is notified. Check `failed_jobs` first when "I got no notification".
- **With a remote database every query costs a network round trip (~350 ms measured), so count queries, not milliseconds of PHP**: run `php scripts/profile-endpoints.php` (`--sql` shows them) after touching a controller / model, and keep a page at its few unavoidable queries. Sessions and cache are **files** (`SESSION_DRIVER=file`, `CACHE_STORE=file`); `Setting::get()` is served from ONE cached array (never `DB::table('settings')` for a read; `set()` forgets it), the bell's `UserNotification::state()` is cached per person (any new write to `user_notifications` must `Cache::forget('notifications.state.' . $id)`), and `PaymentMethod::activeOptions()` is remembered for the request. `DB_PERSISTENT=true` reuses the connection between web requests (`AppServiceProvider::sendConnectionSetupOnce()` sends the charset / strict mode once). Test caches with the `array` store, so a test that writes `settings` / `user_notifications` with raw `DB::table()` can read a stale value: go through the model. In production run `php artisan optimize` (config / route / view / event cache) on every deploy, with `APP_DEBUG=false`; `public/hot` (the Vite dev server) makes every page slow, delete it and `npm run build`.
- **Cached reads are dropped by the write, not by you** (`App\Support\TableCache`, `AuthCache`): ONE listener (`TableCache::watch`, `AppServiceProvider`) bumps the version of every table any non-SELECT statement writes, so master data, the staff feeds, a customer's plain My Orders pages and the signed-in user (+ roles + permissions, `AUTH_CACHE_TTL`) are never stale after a normal write. **When you add a cached read:** use `TableCache::remember([tables], 'key', fn)`; it must not depend on `now()`, the auth user or a request value (compute a clock status AFTER the cached rows, as `OrderSession::getAll` does); name EVERY table it reads, joins included, plus tables a foreign-key CASCADE writes (the listener cannot see a cascade); never build the key from text a user types (cache-file spam). Tests that change these tables with raw SQL are fine (the listener sees them); a test that edits the database through another connection is not. The `array` cache of the tests hands back the same objects, so do not mutate a returned row. In production with several app servers set `AUTH_CACHE_TTL=0` and use a shared cache (Redis).
- **Never do cache (or any database) work inside a `DB::listen` callback.** `TableCache::watch()` used to write the cache there: with `CACHE_STORE=database` that insert ran in the middle of the caller's statement, and on SQLite it replaced `lastInsertId`, so `insertGetId` returned the CACHE row's id (`migrate:fresh --seed` died with a foreign key error in `PermissionSeeder`: the role got the wrong id) and a missing `cache` table (migrate:fresh builds the schema first) threw. The listener now only notes the table; `flush()` / `settle()` do the writes later and swallow errors, and a finished migration flushes the cache. If you change it, run `php artisan migrate:fresh --seed` on a scratch SQLite file with `CACHE_STORE=database` AND `file` (never against the real database: it drops every table).
- **No per-row queries in a loop, and never `QUEUE_CONNECTION=sync` in production.** Saving a list of dishes did a read + a write per dish (~100 queries for 30 dishes, each insert its own commit): read the existing rows ONCE (`whereIn` + `keyBy`), `insert()` the new ones as ONE array, wrap the whole save in `DB::transaction`, and validate a posted id list with `Controller::dishExistsRule()`, not `'ids.*' => 'exists:...'` (one query per element). With `sync` the web request itself sends every notification / email (42 emails in one "Add Session" click): keep `database` + a worker (cron every minute on shared hosting, see architecture.md).
- **A table that grows per order must be paged by the server, not loaded whole** (Orders and Payments are: `ServerTable`, `Order::staffPage()`, `Payment::staffPage()`; a request with `draw` = one page, without it = everything, for tests and scripts). When you touch them: a new sortable column needs its column index in the model's `$sorts` map; a new filter needs the request key in `ServerTable::filters()`, the narrowing in `staffNarrowed()`, the control read in the page's `ajax.data`, and NEVER a `table.search.fixed(...)` or `table.rows()` over all rows (the browser only holds one page; the popup and cards use the current page's rows). yajra must not search / order again: keep `->filter(fn () => null)->order(fn () => null)` and `setTotalRecords` / `setFilteredRecords`. Export fetches the matching rows in 500-row chunks (cap 5,000) and renders them with a hidden DataTable made from the page's `columns` (`table-export.js`): a column's render function must work on a row object alone. Check a change in a real browser against a seeded DB (scratch SQLite, `php -S` with Laravel's `server.php` router, not `public/index.php`, or the JS files come back as HTML).
